# 組み合わせセット（異種ミックス）要件定義

**日付**: 2026-08-16  
**状態**: すり合わせ確定（未実装）  
**対象**: 出品マスタ／AI情報取得data／将来の在庫  
**親**: CURRENT_PHASE／本スレ（Keepa誤紐づけ、B上限3、構成表、価格・大きさ、列）

---

## 0. ゴール一文

異種の単品を1つの販売商品にする。中身は最大5品番。入力は商品名、マスタに残すのは単品の親番号と個数。競合価格は各単品の最安の足し算を今の競合価格列に書き、その後いまの自店価格提案を使う。大きさは縦・横・高さを単品の同じ辺の足し算。Keepaの表と商品の対応ズレは先に直す。在庫の増減は今のマスタではやらない。あとで「持っている袋の総数」と「組み合わせ×セット数」で単品の1袋を減らす。

---

## 1. 背景（なぜ必要か）

- チーズかつお＋食べるおだしのような行は、組み合わせそのものの競合ASINが Keepa に無いことが多い。
- なのにマスタに単品の競合が付いていた。原因は Step1 が「パック内の何番目」と「Keepaシート左からの何ブロック目」を同じ番号で読んでいること。パックが AI の9行目以降でも、Keepaの左端（かつお単品など）を読んでしまう。
- JAN が単品と同じだと、JAN 結びでも単品と混ざる。
- 将来の在庫は、セットを単品の袋に割って減らしたい。そのとき使う「中身の表」を、出品マスタに先に列として置いておく。

コード根拠（Step1）: `menuSetCompositionProposal` が絞った `aiDataRows` の添字 `i` を `getMinPriceAndAsinBySetCountFromAsinPasteBlock(asinSheet, i)` に渡している。Keepa側の `i` はシート左端からのブロック番号。

## 2. やらないこと（聖域）

- 楽天CSVの生成内容を変えない
- Yahoo出品（`Yahoo.js`）を変えない
- Bのステップ順を入れ替えない
- 組み合わせに、単品Keepaの評価◎のASINをそのままコピーしない
- 今のマスタで在庫数を持たない・売れたときに減らさない
- 検索1件目を競合価格にしない（単品側の既存ルール。足し算の入力も「その単品の確定した最安競合」）
- Bの一度の処理上限を 3→4 にしない（時間切れ・途中停止の理由は残っている。Step2は内部切断なし）
- シリーズIDを、異種ミックスの中身リストに使わない（シリーズIDは同じ単品の袋数を揃える用。[B_P1_SERIES_MAKER_CATALOG_REQUIREMENTS.md](B_P1_SERIES_MAKER_CATALOG_REQUIREMENTS.md)）

## 3. すり合わせで確定した選択

| 項目 | 確定 |
|---|---|
| B一度の上限 | **3のまま** |
| AIの中身の指し方 | **商品名と数量**（セットする時点では親番号が無い） |
| 名前の照合 | 商品名＋**卸値(税込)**（同名の取り違え防止。Bの当B集合と同じ） |
| マスタに残す中身 | **単品の親番号（親SKU）と数量**（システムが結びやすい） |
| 中身の最大 | **5品番** |
| 書く場所 | AIに入力。**マスタの親の行**に耐久で残す。子の行（8個セットなど）には同じ5組をコピーしない |
| 運用順 | **単品を先にB**してから組み合わせを書く |
| 8個セットを売ったとき（在庫の約束） | 中身も **8倍**（チーズ8袋＋だし8袋）。今は計算しない |
| 在庫の単位（将来） | 各単品の **1袋の子**。今はマスタに在庫機能なし |
| 在庫の見方（将来） | 持っている袋の総数と、「組み合わせ×その行のセット数」で割る |
| 競合価格 | 各単品のいちばん安い競合を **個数どおり足す**。それを組み合わせの **今の競合価格列** に書く |
| 自店の売る値段 | その競合価格のあと、**いまある価格提案**を回す。人のチェックは今どおり |
| 箱・大きさ | いちばん大きい単品のコピーではない。**縦・横・高さそれぞれ、中身の同じ辺を全部足す** |
| 辺が空・競合が空 | その項目は空＋人が見る印。勝手に別商品を埋めない |
| Keepa | パック内の番号ではなく、**そのAI行に対応するブロック**。組み合わせブロックに◎が無ければ競合は空 |
| 列の追加 | **今の出品マスタに先に足す**（在庫の仕事のとき出品側に列が無いと後で壊しやすい） |
| 列の位置 | **「⇒AI作業エリア」より右**（Bが左〜作業エリアまで式をコピーするため） |
| 列の名前 | 楽天・Yahooの出品項目と同じ名前にしない |
| 自動記入 | 列を足しただけでは **Bは埋めない**。Keepa対応のあと、記入は別承認 |
| 不要列 | **使っていない列は削除**する。先に一覧を出して人が見てから。数式・楽天・Yahooが見ている列は消さない |

### 3.1 途中案で捨てたもの（記録）

- 競合は「参考列だけ」に書き、価格提案は回さない → **不採用**。足し算を競合価格に入れ、既存提案を使う。
- 箱はいちばん大きい単品をコピー → **不採用**。3辺を足す。
- 組み合わせの計算は全部在庫の別仕事 → **列と場所は出品マスタで先にやる**。中身の自動計算はKeepaのあと。
- マスタの中身を商品名のまま残す → **不採用**。入力は名前、残すのは親番号。
- 出品GASはKeepa以外触らない → **列の新設・不要列削除は出品マスタで今やる**（記入ロジックは後）。

---

## 4. データの流れ

1. 人は AI情報取得data に、売るセット1行を書く。中身は構成1〜5の商品名と数量。数量は「セット1個あたり、その単品を何袋使うか」。
2. 単品はすでにマスタに親がある（先にB）。
3. 仕組み（Keepa対応のあと）が、名前＋税込で単品親を探し、マスタ親に親番号と数量を書く。見つからなければ空＋人が見る。
4. 各単品の競合最安×数量を足し、組み合わせの既存競合価格列に書く。
5. 縦・横・高さを辺ごとに足し、大きさに書く。今の送料・自己発／FBA・箱の決め方に乗せる。
6. 今の価格提案で自店価格を出す。人が見る。
7. 将来の在庫: 売れたセット数 × 構成数量 だけ、各単品の1袋在庫を減らす。マスタに在庫列は今は作らない。

---

## 5. 列

### 5.1 AI情報取得data（入力）

- 既存: 商品名、JAN、卸値(税込)、シリーズID など（ミックスにシリーズIDは使わない）
- 追加: `構成1_商品名` `構成1_数量` … `構成5_商品名` `構成5_数量`
- 構成が1つだけ（または全部空）なら今までの単品行。2つ以上埋まればミックス。

### 5.2 マスタ・親の行だけ（耐久）

- `セット構成1_親SKU` `セット構成1_数量` … 最大5組
- `セット構成_状態`（OK／欠け／人が見る）
- 大きさ: 足し算結果（縦・横・高さ。列名は実装時に既存の本体サイズ列とぶつからない名前）
- **競合価格amazon／楽天／Yahoo! は既存列を使う**（足し算結果を書く）
- 在庫数・在庫SKU列は **今は作らない**

子の行の「A.セット商品数」（8など）は売る単位。親の構成数量は「セット1個＝単品何袋」で固定。

### 5.3 列の追加・削除（今の出品プログラム）

- 構成列は **既存列の改名（AR〜BJ付近）**。作業エリア右への新規追加・列削除はしない。出品マッピングに載せない。
- Step1／抜けセット数の式コピーは `セット構成*` を列名で除外する。

---

## 6. 値段のルール（確定）

- かつおの最安競合 ＋ だしの最安競合（×それぞれの数量）＝組み合わせの競合価格。
- 3モールとも同じ足し方（各モールの単品競合列を足す。モールをまたいで足さない）。
- その後、既存の価格提案で自店価格。
- 組み合わせ用の偽ASINは競合店ASINに書かない（Keepa単品の流用禁止）。
- 中身のどれかにそのモールの競合が無ければ、そのモールの競合価格は空＋人が見る印。

---

## 7. 大きさのルール（確定）

- 3辺それぞれ、中身の同じ辺を足す。例: 10×5×2 と 8×4×3 → 18×9×5。
- 実際の荷物より大きく出やすい（安全側）。後で「長い辺だけ足す」等に変えるときはこの節を改める。
- 辺が欠けたら大きさは空＋人が見る。

---

## 8. Keepa（出品GASで先に直す）

- Step1 はパック内の 0,1,2 ではなく、**その商品のAI行に対応するKeepaブロック**を読む。
- セット数の集計（`getAggregatedSetCountsByBlocksFromAsinPasteSheet` の添字）も同じ。
- 組み合わせブロックに◎が無ければ、競合価格・競合店ASIN・URLは空（単品ブロックを使わない）。
- JANだけで全行にKeepaを流さない（親番号の構成と矛盾させない）。
