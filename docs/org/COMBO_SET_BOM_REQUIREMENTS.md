# 組み合わせセット（異種ミックス）要件定義

**日付**: 2026-08-16  
**状態**: すり合わせ確定（未実装）  
**対象**: 出品マスタ／AI情報取得data／将来の在庫  
**親**: CURRENT_PHASE／本スレ（Keepa誤紐づけ、B上限3、構成表、価格・大きさ、列）  
**在庫本線（領域4）**: 分解消費・適正在庫の実装要件は [DOMAIN4_MALL_INVENTORY_ORDER_REQUIREMENTS.md](DOMAIN4_MALL_INVENTORY_ORDER_REQUIREMENTS.md) を正とする（本ファイルの在庫約束は維持）。

---

## 0. ゴール一文

異種の単品を1つの販売商品にする。中身は最大5品番。入力は商品名、マスタに残すのは単品の親番号と個数。Amazon競合は各単品の最安の足し算（Keepa◎優先）。楽天／Yahooはモール検索でセットごとに価格＋URL。大きさは長辺・短辺を最大、一番短い辺だけ数量倍して足す。Keepaの表と商品の対応ズレは先に直す。在庫の増減は今のマスタではやらない。あとで「持っている袋の総数」と「組み合わせ×セット数」で単品の1袋を減らす。

---

## 1. 背景（なぜ必要か）

- チーズかつお＋食べるおだしのような行は、組み合わせそのものの競合ASINが Keepa に無いことが多い。
- なのにマスタに単品の競合が付いていた。原因は Step1 が「パック内の何番目」と「Keepaシート左からの何ブロック目」を同じ番号で読んでいること。パックが AI の9行目以降でも、Keepaの左端（かつお単品など）を読んでしまう。
- JAN が単品と同じだと、JAN 結びでも単品と混ざる。
- 将来の在庫は、セットを単品の袋に割って減らしたい。そのとき使う「中身の表」を、出品マスタに先に列として置いておく。

コード根拠（Step1）: `menuSetCompositionProposal` が絞った `aiDataRows` の添字 `i` を `getMinPriceAndAsinBySetCountFromAsinPasteBlock(asinSheet, i)` に渡している。Keepa側の `i` はシート左端からのブロック番号。

## 3. すり合わせで確定した選択

| 項目 | 確定 |
|---|---|
| B一度の上限 | **3のまま** |
| AIの中身の指し方 | **商品名と数量**（セットする時点では親番号が無い） |
| 名前の照合 | **構成は商品名で単品親を探す**。セット行の卸値(税込)は**単品の和**であり照合キーにしない。同名が複数のときだけ単品側の税込で絞る |
| セットの原価 | 各単品の卸値(税込)×構成数量の**和** |
| マスタに残す中身 | **単品の親番号（親SKU）と数量**（システムが結びやすい） |
| 中身の最大 | **5品番** |
| 書く場所 | AIに入力。**マスタの親の行**に耐久で残す。子の行（8個セットなど）には同じ5組をコピーしない |
| 運用順 | **単品を先にB**してから組み合わせを書く |
| 8個セットを売ったとき（在庫の約束） | 中身も **8倍**（チーズ8袋＋だし8袋）。今は計算しない |
| 在庫の単位（将来） | 各単品の **1袋の子**。今はマスタに在庫機能なし |
| 在庫の見方（将来） | 持っている袋の総数と、「組み合わせ×その行のセット数」で割る |
| 競合価格 | **Amazon**: 各単品のいちばん安い競合を個数どおり足す（Keepa◎がある袋はそれを優先）。**楽天／Yahoo**: モール検索（メーカー＋短名＋N種）→袋数一致の最安を **価格＋URL** で書く。検索0件は空（足し算しない）。選択・よりどり商品は不採用 |
| 自店の売る値段 | その競合価格のあと、**いまある価格提案**を回す。人のチェックは今どおり |
| 箱・大きさ | いちばん大きい単品のコピーではない。**長辺・短辺は構成の最大。一番短い辺だけ数量倍して足す** |
| 辺が空・競合が空 | その項目は空＋人が見る印。勝手に別商品を埋めない |
| Keepa | パック内の番号ではなく、**そのAI行に対応するブロック**。組み合わせブロックに◎が無ければ競合は空 |
| 列の追加 | **今の出品マスタに先に足す**（在庫の仕事のとき出品側に列が無いと後で壊しやすい） |
| 列の位置 | **「⇒AI作業エリア」より右**（Bが左〜作業エリアまで式をコピーするため） |
| 列の名前 | 楽天・Yahooの出品項目と同じ名前にしない |
| 自動記入 | 列を足しただけでは **Bは埋めない**。Keepa対応のあと、記入は別承認 |
| 不要列 | **使っていない列は削除**する。先に一覧を出して人が見てから。数式・楽天・Yahooが見ている列は消さない |

### 3.1 途中案で捨てたもの（記録）

- 競合は「参考列だけ」に書き、価格提案は回さない → **不採用**。足し算を競合価格に入れ、既存提案を使う。
- 箱はいちばん大きい単品をコピー → **不採用**。長辺・短辺は最大、一番短い辺は数量倍して足す。
- 同じ辺どうしを全部足す → **不採用**。長辺・短辺まで足すと実寸より大きくなり箱に入らない。
- 組み合わせの計算は全部在庫の別仕事 → **列と場所は出品マスタで先にやる**。中身の自動計算はKeepaのあと。
- マスタの中身を商品名のまま残す → **不採用**。入力は名前、残すのは親番号。
- 出品GASはKeepa以外触らない → **列の新設・不要列削除は出品マスタで今やる**（記入ロジックは後）。

## 4. データの流れ

1. 人は AI情報取得data に、売るセット1行を書く。中身は構成1〜5の商品名と数量。数量は「セット1個あたり、その単品を何袋使うか」。
2. 単品はすでにマスタに親がある（先にB）。
3. 仕組み（Keepa対応のあと）が、名前＋税込で単品親を探し、マスタ親に親番号と数量を書く。見つからなければ空＋人が見る。
4. 各単品の競合最安×数量を足し、組み合わせの既存競合価格列に書く。
5. 長辺・短辺は最大、一番短い辺だけ数量倍して足し、大きさに書く。今の送料・自己発／FBA・箱の決め方に乗せる。
6. 今の価格提案で自店価格を出す。人が見る。
7. 将来の在庫: 売れたセット数 × 構成数量 だけ、各単品の1袋在庫を減らす。マスタに在庫列は今は作らない。

## 5. 列

### 5.1 AI情報取得data（入力）

- 既存: 商品名、JAN、卸値(税込)、シリーズID など（ミックスにシリーズIDは使わない）
- 追加: `構成1_商品名` `構成1_数量` … `構成5_商品名` `構成5_数量`
- 構成が1つだけ（または全部空）なら今までの単品行。2つ以上埋まればミックス。

### 5.2 マスタ・親の行だけ（耐久）

- `セット構成1_親SKU` `セット構成1_数量` … 最大5組
- `セット構成_状態`（OK／欠け／人が見る）
- 大きさ: 長辺・短辺の最大＋最短×数量（列名は実装時に既存の本体サイズ列とぶつからない名前）
- **競合価格amazon／楽天／Yahoo! は既存列を使う**（Amazonは足し算／Keepa。楽天Yahooは検索結果）
- 在庫数・在庫SKU列は **今は作らない**

子の行の「A.セット商品数」（8など）は売る単位。親の構成数量は「セット1個＝単品何袋」で固定。

### 5.3 列の追加・削除（今の出品プログラム）

- 構成列は **既存列の改名（AR〜BJ付近）**。作業エリア右への新規追加・列削除はしない。出品マッピングに載せない。
- Step1／抜けセット数の式コピーは `セット構成*` を列名で除外する。

## 6. 値段のルール（確定）

- かつおの最安競合 ＋ だしの最安競合（×それぞれの数量）＝組み合わせの **Amazon** 競合価格（Keepa◎がある袋は除く）。
- **楽天／Yahoo** は上記足し算ではなく、ミックス向けモール検索のセット別最安＋URL（§6.2）。
- 1袋がどのモールにも無ければ、そのモールのミックス競合価格は空＋人が見る（Amazon足し算側）。楽天／Yahoo検索0件も空。
- その後、既存の価格提案で自店価格。
- 組み合わせ用の偽ASIN（単品Keepaの◎）は競合店ASINに書かない。
- **ミックス用Keepaブロックに、その袋数の◎ASINがあるとき**: Amazonの競合価格・ASIN・URLはその行を使う（足し算で上書きしない）。無い袋数だけ単品1袋の足し算×袋数。楽天／Yahooは§6.2のモール検索（このKeepa分岐の対象外）。

### 6.1 Bキュー（運用）

- **単品を先にB済**にしてからミックスをBする（§3 運用順）。
- Bキューは **単品のみ** または **ミックスのみ**（同時に混ぜない）。
- ミックスをキューに入れるとき、構成単品がマスタに無ければ **B開始を止める**。
- B開始時、ミックスが含まれるときは人へ **構成単品B済・同時処理しない** を alert。

### 6.2 B Step2.1（12-⑭＋ミックス検索）

- **単品ブロック**: JAN＋セット数で楽天／Yahoo を書く（従来12-⑭）。選択・よりどりタイトルは最安でも不採用。
- **ミックス親**: JAN紐付けでは書かない（単品ヒットの誤載せ防止）。代わりに `applyMixMallCompetitorSearchToMaster_` で **メーカー＋短名＋N種** 検索→袋数一致の最安を **価格＋URL** 書込。
- ヒットは **選択・よりどり除外**のうえ、タイトルに **N種／アソート／詰合せ**等があるものだけ採用（単品N袋の誤載せ防止）。除外後0件なら次クエリへ。
- 袋数はタイトルパース優先。不能かつ画像URLありのとき **Gemini Vision**（親あたり上限・既定5。`MIX_COMPETITOR_SET_COUNT_FROM_IMAGE` 未設定=ON、`=false` で無効）。不明は空。
- Vision は文字列抜き出し→売りの個数／中身の数に分類→**confidence=high のみ採用**。単位は袋に限定しない（個・パック・本・缶・食・箱・セット等）。
- **単品12-⑭**も同ロジック（タイトル不能時のみ）。スコープJANに限り、1実行あたり上限既定5（`COMPETITOR_HIT_SET_COUNT_FROM_IMAGE` / `_LIMIT`）。コスト抑制。
- 対象子行は楽天／Yahoo競合を一旦空にしてから書込（旧足し算の価格のみ残骸を残さない）。検索0件のモール／袋数は空。
- ミックス検索が0件のモールは **空のまま**（単品足し算フォールバックなし）。
- R12 Step1 の楽天／Yahoo足し算書込は廃止。Amazon足し算／Keepa◎は従来どおり。

**保留（2026-08-23・G7）**: 楽天に当該セット数の適切な競合が無いとき、広い検索が別商品の汎用セット（例 5個7207・同一店URL）を複数ミックス親に載せることがある。**非クリティカル**（正競合無し時の参考値程度）。問題拡大までコード改修しない。合否は [B_RERUN_CLEAR_AND_JUDGE_HUMAN_RUN.md](B_RERUN_CLEAR_AND_JUDGE_HUMAN_RUN.md) §4.3。

### 6.2.1 ミックスのセット数（2026-08-21 確定）

- **`A.セット商品数`＝何セットか**（各種あたり）。合計袋数（種×各）ではない。例: 各1袋（3種）→**1**／各2袋（3種）→**2**。
- タイトル: 「各N＋単位」→ N。単位は袋・個・缶・本・箱・パック・セット・食・枚・杯・瓶・組・足・着・ロール・ケース・ボール・カートン・丁・玉・尾・束 等。「計N袋」最優先は **ミックスでは使わない**（単品12-⑭の共有パースとは分離）。
- 種だけ・各なし → 仮に1セット → 画像で確認。**画像が違えば画像優先**。
- 画像: メインのみ。セット数 Vision ＋ 参考情報(画像URL) との一致ゲート（◎と同じ閾値。合否のみ）。親あたり上限既定 **20**（`MIX_COMPETITOR_SET_COUNT_FROM_IMAGE_LIMIT`）。
- 単品の `parseSetCountFromItemNameWithSource`（計N袋・種×各）は **変更しない**。

## 7. 大きさのルール（確定）

**人は寸法を書かない。** 測らせない。

### 計算の本線
1. ミックスの各構成は、マスタの **単品親SKU** で結ぶ。
2. その単品親に紐づく **競合情報**（`競合店ASINコード`／競合Amazon URL → Keepa キャッシュの梱包3辺 `梱包_L/W/H_cm`）から、幅・奥・高を取る。L→幅、W→奥、H→高。3辺すべて >0 のときだけ採用。
3. 照合するセット数は **常に1袋**（構成数量は「何袋積むか」。足すのは一番短い辺だけ）。
4. 各構成の3辺を短い順に並べ、**長辺・短辺（残り2辺）は最大のまま。一番短い辺だけ数量倍して足す**。例: 21.8×15.1×2.5 と 21.8×15.1×2.5 が各1袋 → **21.8×15.1×5**（同じ辺を全部足す 43.6×30.2×5 は禁止）。書いた列は 幅=長辺、奥=短辺、高=最短の和。
5. 結果をミックス親の `セット構成_幅/奥/高_cm` と既存の梱包3辺（`梱包:幅(cm)` または `(梱包:幅(cm))`）へ同じ値で書く。子の構成列にはコピーしない。
6. **送料・サイズ（子行）** は単品と同じ。親の1袋3辺を物流の寸法入力にし、袋数だけ積んで箱を選ぶ。AI情報取得data の梱包が空でも、親のセット構成3辺があれば寸法なしにしない。

### 競合情報が無いとき
- **同じシリーズ**（AI の `シリーズID` が同じ。JAN経由でマスタ単品と結ぶ）の別ASINから寸法を流用してよい。シリーズID空は流用しない。
- **セット数（マスタ `A.セット商品数` および Keepa `setCount`）が1以外のものは参考NG。** 1袋の寸法に8袋の外箱を使わない。逆も禁止。Keepa の setCount が空なら、マスタ行のセット数が1（親行で空は Keepa 側が1または空のときだけ）なら採用可。
- シリーズ内に「1袋」で寸法があるASINが無ければ、その辺は空＋状態「人が見る」。

### 価格・ASINとの切り分け

- ミックス用Keepaにその袋数の◎が無いときの競合**価格**は、単品の最安×数量の足し算。
- ミックス親の **競合店ASINに単品◎を書かない**（偽ASIN禁止）は維持。ミックス用ブロックの◎はその袋数の子行に書いてよい。
- 寸法のシリーズ流用は **大きさ専用**。価格の最安探しをセット数無視で混ぜない。
- **`FBAティア`／`FBA手数料_円`（親）**: 1袋子のミックスKeepa ASIN で Catalog する。親の競合店ASIN／N列には書かない。Catalog **梱包が空**なら `セット構成_幅/奥/高_cm`（BC〜BE）と Catalog 重量（あれば）で設定マスタ判定して書く。1袋◎が無く BC〜BE も空なら空のまま。
- **`サイズ＆自己発/FBA`（CQ）**: 箱名は袋数ごとなので **子行が正**。親 CQ に上げない。BC〜BE の cm を CQ にコピーしない（型が違う）。

同じ辺を全部足すと実寸より大きくなり、箱選定不能になる。長辺・短辺は変えず、最短だけ積む。

## 8. Keepa（出品GASで先に直す）

- Step1 はパック内の 0,1,2 ではなく、**その商品のAI行に対応するKeepaブロック**を読む。
- セット数の集計（`getAggregatedSetCountsByBlocksFromAsinPasteSheet` の添字）も同じ。
- 組み合わせブロックにその袋数の◎があれば Amazon はそのASINの値段。無ければその袋数は足し算。単品ブロックの◎は使わない。
- JANだけで全行にKeepaを流さない（親番号の構成と矛盾させない）。

## 10. 検収の目安

- チーズかつお＋だしの親に、かつお単品KeepaのASINが付かない（Keepa対応後）。
- 構成列に、単品の親番号と数量が入る（自動記入を入れたあと）。
- ミックス用Keepaにその袋数の◎があれば、DCはその値段（足し算しない）。無ければ足し算。
- 子行のサイズは、親のセット構成1袋3辺を単品と同じ箱選定に渡す。AI梱包が空でも寸法なしにしない。
- 親の `FBAティア` は1袋子のミックスKeepa ASIN で Catalog。梱包が空ならセット構成3辺で書く。親の競合店ASINは空のまま。自己発CQは子行。
- 1袋欠けを別モール1袋で埋めたときは状態「人が見る」。袋数違いは使わない。
- 大きさが、単品親の競合（Keepa梱包・1袋）の長辺・短辺の最大＋最短×数量になっている。競合が無ければ同シリーズ1袋の流用。セット数違いは使わない。
- 楽天CSV・Yahoo出品の項目が増えていない。
- 8個セットの在庫計算は、在庫PJで 8×各構成数量 になること（今は未実装でよい）。
