## 0. 目的（1文）

**セラー台帳を枯渇させず**、**店は軽く・メーカーは1社完走ずつ**回し、人は **実態check と見積判断** だけに寄せる。

---

## 1. 背景・問題

| 問題 | 本要件での解 |
|------|----------------|
| 店1件通しが重い（query＋product＋門＋①候補） | **A-light** で店フェーズを分離 |
| 週1メーカー決定で待ちが発生 | **完走→即次1社**（⑧の「週待ち」運用は廃止） |
| 複数メーカー同時洗いは見積が散る | **常に1社完走**（既存ロックと一致） |
| セラーが尽きると店レーンが止まる | **レーン0 セラー貯め** をサイクルに明示 |
| 前回簡易版でセラー貯めが抜けていた | 本書で **3レーン** として固定 |

## 2. 3レーン（正）

```text
[0] セラー貯め … 競合DB「セラー」へ新規 sellerId（§5.4・C0 実装後）
[1] 店 A-light … レ点店を調査しメーカー名＋累計ヒットを更新
[2] メーカー B→D … 1社完走 → D1→D2 → 即次1社
```

### 2.1 レーン間の依存

| レーン | 入力 | 出力 | 止まる条件 |
|--------|------|------|------------|
| **0 セラー貯め** | 門通過 ASIN（Keepaフル BB ＋ SP-API 新品オファー） | `セラー` 新規行（調査CK **OFF**） | 門通過 ASIN なし |
| **1 A-light** | `セラー` の調査CK=TRUE | `抽出メーカー`・食品比率・サマリ追記。**セラーヒット再計算は競合GAS**（①は待たない） | **未調査店（レ点可能）が無い** |
| **2 B→D** | メーカーサマリ（自動選定1社） | 洗い完走・①候補・品番リスト・見積候補 | 洗えるメーカー（実態OK・未調査）が無い |

**フィードバック**: レーン2 の門通過 → レーン0（C0 後）→ レーン1 の店プール補充。

**A 契約の変更**: 従来 A は query ASIN を倉庫・①候補へ渡す。**A-light では門・①候補・店ASIN倉庫を行わない**。①候補／D の材料は **レーン2（メーカー Catalog 完走）のみ**。

### 2.2 A-zero は不可

`/query` のみでは **メーカー名が取れない**。店レーンは **A-light** が下限。

## 4. レーン1 — 店 A-light（2026-08-30 改訂）

### 4.1 やる／やらない

| やる | やらない |
|------|----------|
| Keepa `GET /seller` storefront=0 | **門** |
| Keepa `GET /query`（調査カテゴリ・ページ送り） | **①候補** |
| Keepa `GET /product` **メーカー名のみ**（スライス） | **D1/D2** |
| `セラー` 更新・`抽出メーカー`・規模帯 | Keepaフル **upsert** |
| サマリ行追記（実態シード） | メーカー洗い。**セラーヒット／小規模出現の数え直し**（競合GAS §5） |
| トークン不足時は **温和停止＋トリガー続き**（1店を完走） | storefront=1 全ダンプ |

### 4.1bis 調査カテゴリ・SKU見積・構成比の分担（2026-08-30 了承）

**調査カテゴリ（入力）**: 調査複製 **`①プロファイル`**。最左に **`調査カテゴリー`**（チェック）と **`AmazonルートID`**（数字）。`調査カテゴリー=TRUE` かつルートID非空の行だけが `/query` の対象。初期は **`食品・飲料・お酒` のみ ON**（AmazonルートID=`57239051`。競合DBルート列と同名。カテゴリ名を「食品」に短くしない）。`共通` 行・カテゴリが数字のみの行は対象外。レ点0行は `57239051` へフォールバック＋①ログ警告。門の閾値行選択（マッチ語）とは **別列**。飲料・お酒の除外はルート変更せず門・後工程。

**調査カテゴリ外は載せない（2026-09-20／Catalog前倒し 2026-10-24／親辿り 2026-10-28）**: メーカー洗いの Catalog 列挙は **調査カテゴリ ON のルート以外をキューに入れない**（`includedData=classifications`・ルートID／名前照合。欠測も入れない）。照合は分類ノードの **`parent` を辿り**、チェーン上に許可ルート（例: 食品 `57239051`）があれば残す（先頭ノードだけだと下位IDになり食品が落ちる）。Keepa 前に切るので同名ブランドの食品外ASINでトークンを払わない。門・D1・D2 も従来どおり Keepa ルートで落とす（二重）。切戻し **`PR_CATALOG_SURVEY_ROOT_GATE=false`**（旧: Catalog は社名＋タイトル含有のみ。ルートは門だけ）。親辿りだけ切る切戻し **`PR_CATALOG_CLASSIF_WALK_PARENT=false`**。門側全体の切戻しは `PR_SURVEY_ROOT_GATE=false`。

**Catalog タイトルゲート（2026-10-27）**: **既定OFF＝OR**。規模帯も洗いキューも、メーカー名検索ヒットのうち調査カテゴリOKは **商品名にメーカー名が無くても入れる**（商品名ヒットは含まれる。ノーブランド可）。旧「検索∩タイトル含有」は **`PR_CATALOG_TITLE_GATE=true`**。

**調査ルート落とし診断（2026-10-27）**: ①ログ `survey_diag` に `allow=`（プロファイルONの ID:ラベル）と `dropTop=`（Amazon側 rootId:名前=件数の上位）。`miss=`は分類欠測。切戻し `PR_SURVEY_DROP_DIAG=false`。

**調査カテゴリ外は洗わない（選定・続き・2026-10-19）**: メーカーサマリ **`Amazonルートカテゴリ`**（`|`区切り）が調査カテゴリ ON のラベルと **1つも重ならない**社は、C3／帯プール／Catalog未了列挙／洗い続き／洗い本体／レ点洗いから外す。状態は **調査対象外**（進捗 `survey_root_out`）、調査CKは外す。ルート列が空の社はここでは落とさない（既存の食品0%店除外などに任せる）。切戻しは同じ `PR_SURVEY_ROOT_GATE=false`。

**SKU見積（計測の正・店規模）**:

| 項目 | 正 |
|------|-----|
| **理想** | 在庫があるSKUのみ（在庫なしは調査不要） |
| **計測** | Keepa `/query` の **`totalResults`** ＝ **調査対象カテゴリ・現在出品中SKU見積**（近似） |
| **やらない** | `/product offers=20` 等による在庫の事前サンプリング（トークン過多・中止） |
| **やらない** | `カテゴリ構成`／`食品比率`／`ストアASIN数` から規模帯を計算すること |

**カテゴリごとの測り方**:

| 項目 | 正 |
|------|-----|
| 規模測定 | レ点カテゴリ **1行につき query page0 を1回**（`rootCategory`＝その行のIDのみ）→ カテゴリ別 `totalResults` |
| A-light の ASIN 取得 | レ点カテゴリを **OR 1本の query** でページ送り（測ると歩くは分ける。union） |
| トークン（測定） | 約11 × レ点カテゴリ数（店1件・page0） |

**セラー列（出力・競合DB `セラー`）**:

| 列 | 役割 |
|----|------|
| **`在庫SKU見積`** | 店の代表件数（下記ルール） |
| **`規模帯`** | 店の代表帯（小／中／大／特大） |
| **`SKU見積内訳`** | レ点 **2カテゴリ以上**のとき必須。例: `食品:480\|おかし:40`。1カテゴリのみなら省略可 |
| **`規模帯内訳`** | 同上。例: `食品:大\|おかし:小` |
| **`asinList件数`** | 互換。A-light 完了時に代表件数と同値を書いてよい |
| **`カテゴリ構成`／`食品比率`／`ストアASIN数`** | **店の性格・優先・食品0%除外**用。規模帯の入力に **使わない** |

**代表値・特大 hold**:

| 判定 | ルール |
|------|--------|
| 各カテゴリの帯 | そのカテゴリの SKU見積だけで §4.2 の閾値 |
| 店の **`規模帯`** | レ点カテゴリ帯の **最大**（大と小 → **大**） |
| **特大 hold** | **いずれか1カテゴリ**の見積 ≥901 → 特大・フルしない（カテゴリ合算でまたがない。様子見・旧501） |
| 合算件数 | 帯判定に使わない。必要ならログ／任意列で可见化可（実装時） |

**見る場所**: レ点＝調査複製 `①プロファイル`。結果＝競合DB `セラー` の上記列。メーカーサマリの `規模帯`（Catalog）と混同しない。

### 4.2 セラー規模帯（店のSKU見積・2026-09-15 様子見）

メーカー洗いの帯（Catalog 小≤100／中≤300／大≤500／特大≥501）と **数字は別**。店だけ広げる。

| 帯 | SKU見積（カテゴリ単位） | 店フル調査 |
|----|-------------------------|------------|
| **小** | ≤300 | **する**（1店ずつ・続きあり） |
| **中** | 301–600 | **する** |
| **大** | 601–900 | **する** |
| **特大** | ≥901 | **フルしない・名取りしない**（規模測定のみ。巡回日は書く。名取り日は書かない） |

切戻し: `PR_SELLER_BAND_S_MAX=100` ／ `PR_SELLER_BAND_M_MAX=300` ／ `PR_SELLER_BAND_L_MAX=500` ／ `PR_QUERY_TOTAL_HOLD=501`。浅い名取りに戻すなら `PR_ALIGHT_XL_EXTRACT=true`。

すでに測り終わった店（巡回日あり）は自動ではやり直さない。様子見はこれから測る店。

閾値は当面この様子見。レ点を食品以外へ広げる直前に、代表店の内訳を見て必要なら再確認。

**小中=0でも余力あり列挙（2026-10-25 案A／2026-10-26 強化）**: 旧は余力あり＝列挙OFFのため `sm=0`・`unk` 大量・`tok=ample` で店だけ回り Catalog が進まなかった。**`sm=0` かつ Catalog待ちありなら余力ありでも `catalog_first`**。**店の名前取り続きより列挙を先**（ログ `yield_alight_for_enum_sm0`）。列挙後も `sm=0` なら `skip_enum_once` を剥がす。連続 force が既定3回で1回店へ譲る。切戻し `PR_CYCLE_ENUM_WHEN_SM0=false`。U≥31ゲートは付けない。

**注（2026-10-24）**: 「余力ありなら C0 を飛ばして大特大」は **誤りとして撤回**（`PR_C0_YIELD_WASH_WHEN_AMPLE` 未設定=OFF）。正は小中が空かないこと。C0居座り＋満タンは、**レ点／名前取りが枯れて C0 だけ残っている**のが要因。直すのは大特大への逃げではなく、小中補充（②①／実態）の再開。

**競合GAS（別時計。①を止めない）**

```text
起きる
　├ 巡回日がある店数が前回と違う → 当たり直し（全店再走査。足し算しない）
　└ 同じ → 何もしない
```

**1軒ルール（2026-09-19）**: 店は洗いより先に来ない。洗いスライスのあと、小中が閾値未満なら1回だけ店／実態AI。印 `PR_CYCLE_SHOP_AFTER_WASH`。店が終わったら `PR_CYCLE_WASH_BEFORE_NEXT_SHOP` を書く（当たり直しは待たない）。列挙は洗い印を消さない。店フル途中でも予約以下なら洗いへ譲る。洗いキュー未済は続きではない。切戻し `PR_HIT_RECOUNT_OWNER=hb`（①が名前取りのあと数える旧動作）。

**使えるのは「順位が1つも付いていない」だけ。** これは `stats空`／`順位欠測` とほぼ同じ集合で、通過側の誤検出は1%。例外2件も説明がつく（`stats空` で順位ありの1件は冷凍かき揚げで684,356位＝どうせ落ちる／通過で順位なしの1件は黒糖本舗垣乃花の3袋セット＝新しいセット品で順位未付与）。

### 6.5.3 正

- 列挙の Catalog は `includedData=summaries,salesRanks`。`rankN`（`displayGroupRanks`＋`classificationRanks` の個数）を持つ
- **順位の値で落としてはいけない**。Amazon 順位と Keepa 順位の閾値を同一視しない
- 判定に使うのは `rankN === 0`（順位が1つも無い）だけ
- **段取りを飛ばさない**。`PR_CATALOG_RANK_PROBE`（記録だけ）で `noRank` の実測を取り、そのうえで `PR_CATALOG_RANK_CUT` を ON にする
- `rankN` は probe OFF のとき **-1（判定不能）**。`0` と混同しない

## 6.6 完走後の店レーンが居座って Keepa が止まる（2026-09-13 実測）

### 6.6.1 実測

2026-09-13 03:00〜04:20 の1.5時間、**洗い0件**。Keepa は満タン（`liveLeft=300`）でトークン待ちではない。

```
pick_end elapsedMs=197472 parent= via=deferred_all
no_continue_deferred deferred_skip n=8 伊藤園@queue:defer_xl_sm_remain sm=1 unk=0
heartbeat pool sm=1 unk=0 L=27 XL=73 cont=none
heartbeat action=alight shop_after_sm parent=ココウェル shops=26
```

同じ形が 09-12 22:17〜22:24 にも出ている（`効率合否 FAIL cause=no_slice_stall` 計22回）。

### 6.6.2 原因

`prNextHeartbeatAction_` の判定順は **Keepa中続き** → **店フル途中（予約以下なら洗いへ譲る）** → **shop_after_sm（1回）** → **列挙1回** → **洗い後補充1回** → **余力中以上なら洗い** → **余力なしは時計**。洗いキュー未済は続きにしない。余り1軒（`one_shop_yield`）は洗いより先に置かない。

`shop_after_sm`（§6.3bis 案B「Keepa完走直後は店レーンを1回挟む」）は、`prCycleClearShopAfterSm_()` が**自動レ点・A-light・C0 の3つとも0になるまで呼ばれない**。店の未調査が26社あれば毎回 `alight` を返すので、心拍は永久に `wash_small` に届かない。

そこに `defer_xl_sm_remain`（小・中が1社でも残る間は大・特大を洗わない）が重なる。

| 要素 | 状態 |
|---|---|
| 小・中で洗える社 | **1社** |
| その1社 | 心拍が `shop_after_sm` を返すので順番が来ない |
| 大 | 26社・全部 `defer_xl_sm_remain` |
| 特大 | 76社・全部 `defer_xl_sm_remain` |
| Keepa トークン | 300（満タン。回復ぶんが捨てられる） |

**1社が102社を止める。** 小の消化がほぼ終わり（96完了・71保留・24空欄）、残りが大26社・特大76社になったため表面化した。`PR_CYCLE_ENUM_STOCK_N=3` で1回の心拍が増えたぶん、到達が速くなった。

### 6.6.3 正

- `shop_after_sm` / `shop_after_large` は **1つ返したら印を消す**。次の心拍は洗い／列挙に戻る
- 店レーンの本体は `smN < 3` の `prCycleShopBeforeLargeAction_` 側（§4.4）。ここを1回で降りても店の消化は止まらない
- `defer_xl_sm_remain` の優先順（小→中→大→特大）は**変えない**
- `効率合否 FAIL cause=no_slice_stall fixHint=check_phantom_or_pool` はこの形を検出できている。**検出はするが直さない**ので、FAIL が出たら選定プールの内訳（`sm=` / `unk=`）を見る

**残るリスク**: `sm>0` の1社が別の理由（列挙失敗・幽霊）で進めない場合は、印を消しても同じ停止になる。そのときは `no_slice_stall` が再び出る。`smN>0` でも一定時間進まなければ大・特大を通す案は、小中優先を崩すので未採用。

### 6.8.1 実測

### 7.5 生存番犬（心拍が止まらない・2026-08-27／28）
