## 1. 目的（ハイブリッド）

| レーン | 内容 | 自動化 |
|--------|------|--------|
| **A. 期間限定値下げ** | SP-API `purchasable_offer.discounted_price`（開始・終了） | **安定するまで承認制**（設定のたびメール承認→送信）。安定後に継続自動へ緩和可 |
| **B. 公式タイムセール** | SC推奨テンプレ編集 → 提出用.xlsx → 人が一括管理へUL | **半自動**（生成・判定・メールまで／ULは人） |

平時はAで手間を減らし、公式枠があるときだけBに切り替える。

### 1.1 既存の「別の自動値下げ」とのぶつかり

| 既存機能 | 何をするか | 本レーンAとのぶつかり |
|----------|------------|----------------------|
| `AmazonSpapiPut.js`（D出品） | 出品・オファー登録時に **販売価格（our_price）** を送る | **常時の期間セール自動ではない**。出品タイミングで価格を送ると、Aのセール価格と一時的に競合しうる |
| リサーチ／価格戦略のマスタ書き込み | 提案をマスタ列へ | Amazonへ直接送らない限り衝突しない |
| 自動価格ルール（Automate Pricing） | 本PJでは**未導入** | 現状なし |
| 本レーンA | 期間付きセール価格の付与／解除 | — |

**結論（現状）**: 「別系統の期間値下げボット」は無い。ぶつかりうるのは **D出品PUTが同じSKUの価格を上書きする**場合。  
**対策**: A実行対象は **SKU単位**。同一SKUでD出品PUTと時間的に重なるときは **Aをスキップしてメール**（またはD完了後にA再実行）。安定後もこの排他を維持。

## 1.2 レーンA承認フロー（安定まで）

```text
人がマスタに SKU・価格・期間・数量方針を入力
  → システムが提案メール（価格・数量・期間・利益概算・目的＋手順）
  → 社長（当面）が承認（メール返信 or マスタ「承認済」チェック）
  → 承認済み行だけ dry_run → 本番送信
  → 失敗時: 最大2回リトライ → ログ → メール
```

安定後に「承認なし継続自動」へ緩和する場合は、別途マトリクス更新と社長明示が必要。

- **ポイント***: §10.10（期間中／セール前退避／現在の出品者付与%。店頭合計％ではない）
- **実質戻し***: §10.12／§10.14。人必須=`目標売価円`＋`販促ポイント%`。進捗の正本は `減衰中ポイント%`＋`出品者ポイント現在%`。起動は **E先行**（§10.14）
- **レーンA実績***: `A実施`／`A最終送付日時`／`A期間`／`A価格円`／`Aログ参照`
- **適用**: GAS **99-②** 列並び／**99-③** ヘッダ色・数式、または `python sync_master_and_exec.py --schema-only`
### 2.3 ヘッダ（`タイムセール`）

`sale_id`／`レーン`／`SKU`／`ASIN`／`親ASIN`／`商品名`／`画像`／`marketplace`／`通貨`／`有効`／`承認済`／`種別`／`スケジュール`／`開始日`／`終了日`／`出品者価格_SC`／`タイムセール価格_SC`／`タイムセール価格_確定`／`販売商品数_SC`／`V30`／`販売商品数_確定`／`通常価格`／`セール価格`／`目標販売`／`想定利益`／`原価U`／`提出対象`／`状態`／`更新日時`／`runId`／`メッセージ`／`メモ`

- **画像**: 商品名直後。`=IMAGE("URL")`（埋め込みバイナリではなく数式＝ファイル軽量）
- **販売商品数_確定**: §10.2（`ceil(V30/30×D×M)`・下限30・イベントM=3・FBA×0.85上限）

空欄可（A行はスケジュール以外のB列が空でもよい）。

P1bは **レーン=B_公式 かつ 提出対象=はい かつ 名付き公式スケジュール** のみxlsxへ。  
提出xlsxは **対象SKU行のみ**（`submit_targets_only`、既定true）。②テンプレの非対象・数量限定行は削除して出力する。  
Amazon推奨テンプレは同一スケジュールで **スケジュール／開始／終了を縦結合**することがあるため、生成時に**データ行の縦結合を解除し、1行ごとに値を書き戻す**（結合のまま行削除するとUL不能）。ヘッダの結合は維持。  
提出時の種別は **おすすめタイムセールのみ**（数量限定は参加させない／行ごと削除）。
sync入力の名簿は **マスタ有効のみ**（施策シートからは起こさない。初回のみマスタ空なら施策から復元可）。

## 7. レーンA（`discounted_price`）の仕様メモ

- Listings Items API で期間付きセール価格を patch／merge。対象は **SKU**（marketplace=JP、通貨=JPY）  
- **公式特集枠は付かない**。取り消し線はAmazon判定次第  
- **安定するまで承認制**（§1.2）。dry_runトグル・runIdログ必須  
- 失敗時: **自動リトライ最大2回**（失敗側のみ）→ログ→**メール必須**  
- 公式モード中はAを停止（§3）  
- 同一SKUでD出品PUTと重なる場合はAスキップ＋メール（§1.1）  
- 誤り時: セール価格の削除／修正をAPIで再送可能  

楽天／Yahooの期間値下げは **本要件の対象外（後回し）**。

## 8. バルクファイルの自動取得はできるか（調査結論）

### 8.1 結論

| 手段 | 可否 | コメント |
|------|------|----------|
| **SP-API / Reports API** | **不可** | Deals推奨テンプレの reportType／エンドポイントは公開されていない |
| **Advertising API** | **不可** | 広告レポート向け。タイムセール一括テンプレDLではない |
| **Feeds API** | **不可** | 出品フィード。Deals作成・推奨DLではない |
| **クーポン一括テンプレ** | 別物 | Coupons bulk は存在するが Deals 推奨テンプレとは別 |
| **ブラウザ自動（Playwright等）** | **技術的には可能** | SCログイン→一括管理→ダウンロードを模倣。**規約・2FA・UI変更・アカウントリスク**。要社長の明示承認 |
| **人がDL→Drive所定フォルダ** | **現行正** | GASはフォルダ監視／取込まで自動化可能 |

**公開APIでバルク（推奨テンプレ）を自動取得する方法は、現状ない。**

### 8.2 「自動取得しないと手間が減らない」への回答

ご懸念は正しい。ただし **ハイブリッドなら削減幅はレーンで分かれる**。

| 作業 | 頻度 | 自動取得なしでの手間 |
|------|------|----------------------|
| レーンA 期間値下げ | 日常・多数SKU | **ほぼゼロ**（API完全自動）。ここが本丸の削減 |
| レーンB 推奨テンプレDL | 公式枠のときだけ（年数回〜月曜ごと要否） | **人がSCでDL→Drive**が残る |
| レーンB UL | 公式枠のたび | もともと人（APIなし） |

→ **日常の値下げ自動化は、バルクDL無しでも大きく減る。**  
→ **公式タイムセール側の大幅削減は、推奨テンプレの自動DL（事実上RPA）か、人がDLする運用を週次ルーチン化するまで頭打ち。**

### 8.3 推奨テンプレ取得方針（確定）

| 案 | 内容 | 状態 |
|----|------|------|
| **①（B0＋リマインド）** | 原則**月1**人DL→Drive→取込。**次々回が月次では取れないと分かったら2週に1回DL**。UL直前は都度新規DL | **本線** |
| **②（B2 RPA）** | SC画面からの推奨テンプレ自動DL | **保留**（再開は社長明示時） |

月1／2週1で足りる範囲: スケジュール候補・次々回の把握。  
UL前は必ず新規DL（提出用の鮮度）。

### 8.4 ②保留時のメモ（再開時用）

- SC利用規約・自動化ポリシーに抵触しうる  
- OTP／パスキー／セッション切れで止まりやすい  
- UI変更で壊れやすい  
- 本番無人実行は段階導入が必要

## 9. メール通知仕様（人作業は目的＋手順必須）

人の操作が残る通知は、本文に必ず次を含める。

| 必須ブロック | 内容 |
|--------------|------|
| **目的** | なぜ今この操作が必要か（1〜3行） |
| **やること一覧** | 番号付き。完了条件が分かる粒度 |
| **操作手順** | URL・画面名・クリック順・保存先・注意（2MB・xlsx・新規テンプレ必須など） |
| **システムが済んだこと** | 自動で終わった処理（ON/OFF切替・xlsx生成など） |
| **リンク** | マスタスプシ／Driveファイル／SC一括管理 URL |
| **期限・優先度** | いつまでに（分かる範囲） |

件名は種別が分かること（例: `[タイムセール] 月次・推奨バルクDLのお願い`）。

### 9.1 月次・推奨バルクDL依頼（①本線）

**目的**: 公式Saleのスケジュール候補を更新し、今後の重なり検知・参加計画に使う。

**操作手順（メールにそのまま載せる文面の正）**:

1. Seller Central にログインする。  
2. [タイムセール一括管理（ダウンロード）](https://sellercentral.amazon.co.jp/promotion-central/manage-in-bulk?tab=upload) を開く（「ダウンロード」タブで推奨情報を取得）。  
3. **最新のタイムセール推奨テンプレート（.xlsx）** をダウンロードする。※古いファイルの使い回し禁止。  
4. 所定の Google Drive フォルダへアップロードする（フォルダURLをメールに記載）。  
5. （任意）広告運用スプシのメニューから「推奨取込」を実行。未実装時は担当Agent／メニュー案内に従う。  

**注意**: この月次DLは主に **暦・候補の更新** 用。実際に公式タイムセールを提出する直前は、§9.2 のとおり **もう一度新規DL** すること。

### 9.2 UL前・提出用xlsxアップロード依頼

**目的**: 公式タイムセールをSCに反映する（手数料・審査あり）。

**システムが済んだこと（例）**: 期間値下げOFF／運用モード切替／提出用xlsx生成。

**操作手順**:

1. **（必須）提出直前に** §9.1 と同様に SC から **最新推奨テンプレを再DL** し Drive へ置く（月曜更新のため）。取込が必要な場合はメニュー実行。  
2. メール記載の **提出用.xlsx**（Driveリンク）を確認する。2MB以下・xlsx形式であること。  
3. [一括管理（アップロード）](https://sellercentral.amazon.co.jp/promotion-central/manage-in-bulk?tab=upload) を開く。  
4. 「ファイルをアップロード」で提出用.xlsx を送る。  
5. 「最近のアクティビティ」で処理完了を待つ（目安1時間以内）。  
6. 処理概要をDLし、エラーがあれば修正→再UL。成功分はマスタ／ログの入替ステータスを更新する（手順またはメニュー案内を記載）。  
7. 手数料・承認結果をSCのタイムセール管理で確認する。  

### 9.3 公式枠検知・期間値下げ自動OFF通知

**目的**: 公式Saleと期間値下げの二重適用を避け、人が公式参加を判断できるようにする。

**システムが済んだこと**: 該当ASINの期間値下げOFF／運用モード=`公式Sale手動` など。

**人に求める操作**:

1. メールのASIN一覧と公式セール名を確認する。  
2. 参加するなら §9.2 の流れへ（必要なら価格・数量をマスタで調整）。  
3. 参加しないならマスタで `停止` または参加中=いいえとし、必要なら期間値下げ復帰タイミングを決める。  

### 9.4 公式枠終了・期間値下げ復帰通知

**目的**: 公式枠後に通常の期間値下げ自動運用へ戻す。

**操作手順**: システムが自動復帰済み。メールは事後通知。異常時のみ人が停止手順に従う。

### 9.5 レーンA失敗通知

**目的**: 期間値下げAPIの失敗を回復する。

**操作手順**: runId・ASIN・エラー要約・マスタ該当行リンク・再実行または価格手修正の手順を記載。

### 9.7 公式Sale数量確認メール（開始21日前／14日前）

**目的**: 事前登録済みDealの数量を、開始前に見直すか人に確認する（バルク再ULでは直らないため）。

**システムが済んだこと**: `revise_b_qty` 相当の再計算、現行シート数量、FBA／延期判定の要約。

**人の手順**:
1. メールの「再計算案」と現状数量を比較する。  
2. **改定する** → SCで当該タイムセールを開き、数量を修正→「編集内容を送信」→画面で反映を確認。  
3. **このまま** → 対応不要（メールに記録）。  
4. **見送り／延期** → マスタ／施策で提出対象外・延期とし、必要ならキャンセル手順に従う。  

**送信タイミング（既定）**: 開始日の **21日前** と **14日前**（同内容の再送可。14日前はFBAリード最終確認を兼ねる）。  
**対象行**: レーンBの `予定`／`UL済`／`実施中` 等。**提出対象=いいえの登録済も含む**（数量改定は再バルクではなく画面編集のため）。  
**実装オプション**: `--tol N` で残り日数±N日を拾う／`--today` で予行。

**リンク（スマホ）**: メール内の誘導先は **広告運用スプシの `タイムセール` 行**（Googleスプレッドシートアプリで開く）。  
Seller Central モバイルアプリではタイムセール詳細が確認できないため、**SCアプリへのディープリンクは使わない**。数量の実改定操作は PC の SC Deal 編集画面。

**件名（固定）**: `[amazonタイムセール] 数量確認 （スプシで確認・改定はSC画面）`

**実装**: `tools/amazon_deals_bulk/mail_qty_confirm.py`（下書き `_work/qty_confirm_*.txt`＋スプシ `⏱数量確認メール下書き`。`--send` は Gmail API／SMTP／GASメニュー）。

### 9.6 FBA補充依頼／sale延期通知

**目的**: おすすめタイムセール開始までに欠品を防ぐ。間に合わない場合は参加を延期する。

**システムが計算して載せること**: ASIN／SKU／`Q_deal`／`V30`／`N`／`Q_fba`／`U`／`T`／`L`

**補充が間に合う場合（U>0 かつ 今日≤T）の人手順**:

1. 不足数 `U` と補充期限 `T` を確認する。  
2. Seller Central → FBA在庫管理／納品手続きで納品プランを作成する。  
3. **期限 `T` までにFC到着**するよう出荷する（リード `L` 日を見込む。既定14日）。  
4. 完了後、マスタの FBA補充ステータスを更新する（案内どおり）。  

**間に合わない場合（U>0 かつ 今日>T）の人手順（sale延期）**:

1. 今回は公式参加しない（マスタで参加中=いいえ、または運用モード=停止）。  
2. 提出用xlsxの対象から外れていることを確認する（システムが除外済みならその旨をメールに記載）。  
3. 補充完了後の次回スケジュールで再検討する。

## 10. 公式レーン：数量・価格・FBAロジック（確定）

### 10.1 種別

- **本線**: おすすめタイムセール  
- **数量限定**: 将来オプション（倍率・0.5日換算は別パラメータで温存可）

用語: 社内ではバルク正式名「おすすめタイムセール」を使う。「期間限定タイムセール」はレーンAと混同しやすいので使わない。

### 10.2 販売商品数（割当）

```text
V30 = max(直近30日販売数, 前年同月30日販売数)
      ※前年同月が無い／データ不足の商品は直近30日のみ
D_days = セール日数（開始〜終了・当日終日は両端含む）
M = 2.0（スケジュールに大型イベント名があれば 3.0）
    # 判定語（部分一致）: プライム／プライム感謝／ブラックフライデー／スマイル
R_max = 0.85
Q_min = 30

Q_base = ceil(V30/30 × D_days × M)   # 日販×日数×倍率
if 前回公式が売切（消化率≥95%）: Q_base = max(Q_base, ceil(前回割当 × 1.5))
Q_deal_推奨 = clamp(Q_base, Q_min, floor(Q_fba × R_max))
```

- `販売商品数_確定` は人または「推奨を採用」でxlsxへ。  
- SC事前入力（確定済み商品／販売商品数）がある場合は、逸脱しすぎないようログ比較（初期は推奨優先可）。

### 10.3 必要FBA在庫・補充・延期

```text
N = Q_deal + V30          # 割当＋1か月見込み（二重計上なし）
U = max(0, N - Q_fba)
T = D_start - L           # L既定14日
```

| 条件 | 動作 |
|------|------|
| U=0 | 補充メール不要 |
| U>0 かつ 今日≤T | §9.6 補充依頼メール |
| U>0 かつ 今日>T | **sale延期**（対象外＋§9.6延期メール） |
| 公式xlsx生成時 | 上記チェック必須。延期行は提出対象に含めない |

### 10.4 タイムセール価格

```text
タイムセール価格_確定 = バルク「タイムセール価格」（事前入力）
※ それより高くしない（割引を浅くする＝価格を上げる方向は不可）
※ 0.00／空は未設定→スキップまたは要判断
※ 原価U・手数料見込で利益が赤なら参加見送り提案（人が確定）
```

事前入力は商品ごとに浅い（約5%）も深い（30%超）もある。Amazonの **出せる上限寄りの推奨** として扱い、ご方針「割引はなるべく低く」＝**この値をそのまま上限採用**。

### 10.5 前回売切の定義（固定）

**消化率 ≥ 95%**（売れた数 ÷ 販売商品数_確定）。分母0は売切扱いにしない。

### 10.6 期間設定ロジック（B固定→A空き埋め）

#### 最大期間

| レーン | 上限 | 備考 |
|--------|------|------|
| **B おすすめ** | Amazon制度 **1〜14日**（イベント名付きはイベント指定が正） | バルク候補内 |
| **A 期間値下げ** | **運用上1本最大14日**（連続複数本可） | API。SC月枠に縛られない |

#### アルゴリズム（確定）

```text
1. 最新推奨バルク／カタログから名付き公式Bを列挙（日付順）
2. b_horizon_days（既定90）より先のBは除外。ただし **早期申請割引の締切前**（§10.9）のイベントは horizon 外でも候補に残す
3. Bを非重なり＋おすすめ同士14日で最大 limit_b 件固定
4. B占有の外側に空き区間を作り、ab_gap_days を差し引く
   - gap=0: A終了 = B開始の前日／A開始 = B終了の翌日
5. 各空きに A を最大 a_max_days(=14) で配置（B直前は終端寄せ、B直後は始端寄せ）
6. 最大 limit_a 本（次回・次々回相当）。月枠はA合成に含めずバルクULしない
7. 数量・価格・FBAは各枠に適用。Bのみ提出xlsxへ
```

#### 「次々回まで」

- Bが1件＋後ろの空き → Aは「Smile前」「Smile後14日」など最大2本
- 遠いBFは horizon 外なら、後ろAの終端は「まず14日」で切り、BF接近時に再sync

制約:

- Amazonが候補に出していない **名付きB** は作れない  
- 同一ASINの **おすすめ同士クールダウン（§10.7）** に抵触するBは除外  
- A↔Bの義務空きは **§10.8で実機確認するまで仮説**（`ab_gap_days` で調整）

### 10.7 セール再実施クールダウン（頻度ポリシー・JP）

Amazonは「購入者に毎日新しいタイムセールを提供する」方針のため、**同一ASINの公式タイムセール再実施に間隔制限**がある。

| 種別（JP） | 同一ASINの再実施制限 | 備考 |
|------------|----------------------|------|
| **おすすめタイムセール**（お買い得情報） | **終了日の翌日から起算し、14日以内は再実施不可** | 本線B。運用判定: `次の開始日 - 前回終了日 >= 14` |
| **数量限定タイムセール** | **7日以内は再実施不可** | 本線外（将来オプション） |

**出典・確認**:

- Seller Central ヘルプ「タイムセールについて」系（[G202111490](https://sellercentral.amazon.co.jp/help/hub/reference/G202111490)）。ログイン必須のため本文はSC上で再確認すること  
- 二次整理（2025-06制度変更・Axalpha確認日2025-08-18）: 「7日以内に同じASINの数量限定…できない。また、**14日以内に同じASINのお買い得情報タイムセールを実施することもできない**」（[Axalpha解説](https://www.axalpha.com/blog/%e6%96%b0%e3%81%9f%e3%81%aa%e3%82%bf%e3%82%a4%e3%83%a0%e3%82%bb%e3%83%bc%e3%83%ab%e6%96%99%e9%87%91%e4%bd%93%e7%b3%bb/)）  
- **旧表記に注意**: 変更前の「7日間のタイムセール」解説では再実施 **28日** と書く二次ソースが残る。2025-06以降の「お買い得情報（1〜14日任意）」は **14日** が正。本PJは後者を採用  
- 米国SCフォーラムでは Best Deal **21日**／Lightning **7日** の記載もある。**本PJはJP出品のため14日／7日を正とする**（US値は使わない）

**判定例（おすすめ同士）**:

| 前回終了 | 次開始 | 差（日） | 判定 |
|----------|--------|----------|------|
| 2026-08-23 | 2026-08-28 | 5 | **不可**（14日未満） |
| 2026-08-23 | 2026-09-06 | 14 | **可**（ちょうど14） |
| 2026-09-03（Smile終了） | 2026-11-27（BF） | 十分大 | **可** |

**レーンA（期間値下げAPI）との関係**:

- クールダウン文言の主語は **公式タイムセール同士**  
- A=`discounted_price` は公式タイムセール申請ではない → **頻度14日の対象外と解釈**（一次文書で「A↔Bは0日可」とは明記されていない）  
- **禁止**: 月枠を誤っておすすめとしてバルクULし、続けてSmileもおすすめULすること  
- **同時期間の二重適用は禁止**（B中はA停止）  
- A終了翌日にB開始が可能かは **§10.8の実機結果を正**とする

**システム動作**:

- B枠同士の提案では §10.7 の14日を満たすものだけ残す  
- 数量限定は提出しない（既存方針）ため7日クールダウンは将来オプション時に適用  
- SCが推奨に載せていても、クールダウン抵触なら提案から除外しメッセージに理由を残す  

### 10.8 A↔B間隔の実機検証（確定手順）

**目的**: 自社アカウントで「B登録後に直前AをAPIで載せられるか」を確認し、`ab_gap_days` の運用値を決める。

**手順**:

1. **1SKUのみ**（影響限定）  
2. `python plan_ab_windows.py --gap 0 --today YYYY-MM-DD` で前A終了日を確認  
3. **B（Smile）**: `build_submit_xlsx` → 人がSC UL → **登録成功をSCで確認**  
4. **A**: EC書き込み承認（P1a）後、Smileと**重ならない**期間で `discounted_price` を送信（まず dry_run→prod）  
5. 判定: API受理 **かつ** SCで期間セール表示 **かつ** Smile（B）が要対応・取消にならない → **そのgapでOK**  
6. NGなら gap を **5 → 10 → 14** に広げてA期間を短くし再送（1日刻みはしない）  
7. 結果を本節と `ab_gap_days`（config）に反映  

**後隙**（Smile終了翌日からのA）は別日に同様検証する。

#### 10.9.1 公式Saleの登録タイミング（確定・全イベント共通）

**方針: 名付き公式Saleは候補に出たら即登録**（Smile／感謝／BF等すべて同じ。早期割引の有無で「後回し」にしない。割引締切がある枠はなおさら急ぐ）。

**二段運用 — 即登録 → 接近時に数量確認メール → 必要なら画面で改定**

| 段 | いつ | 何をする | なぜ |
|----|------|----------|------|
| **① 即登録** | **当該ASINの推奨バルク「スケジュール」候補に、その公式枠が表示された直後** | 対象SKUのみ・おすすめで申請＋スケジュール。数量は §10.2 暫定で可。**提出xlsxは必ず②の最新推奨バルクから生成**（価格・候補の鮮度） | 抜け漏れ防止＋（あれば）早期割引。**候補に無い枠は強制ULしない** |
| **② 数量確認メール** | 開始の **21日前**（第1報）と **14日前**（最終・FBAリードと一致） | システムが現行割当・再計算案・FBA・売切リスクをメール。人に「改定する／しない」を確認 | 事前登録済は**バルク再ULでは数量が変わらない**ため、人の画面編集判断を促す |
| **③ 画面改定（任意）** | ②で「改定する」のとき | SC Deal編集で数量（必要なら価格）→「編集内容を送信」。足りなければ補充or延期 | 反映の正本は画面編集 |

**GASメニュー（`⏱ Amazonタイムセール・ポイント減衰設定`）**:
1. 人: SC→推奨バルクDL → フォルダ **`02.amazon公式タイムセールバルクファイル保存（人間が保存）`**
2. **1. 公式タイムセールの提出xlsxを作る（Agent依頼文）** … ②確認 → Cursor文（**ダイアログ下部にUL固定手順**）
3. Agent: `sync_master_and_exec.py --write` → `build_submit_xlsx.py --write` → **`03.…作成（Python作成⇒人間がUL）`**
   - 選定正本は **②の当該SKU行のスケジュール列ドロップダウン（日付付き全候補）＋セル値**（ValidationカタログだけのBF等は入れない）
   - 状態 `UL済`／`実施中` は再提出しない（再ULリスク回避）
   - ②の日付付きカスタム／月は公式と非重なりなら提出対象へ（日付はAmazon枠のまま。公式と被れば短縮しメール通知）
4. 人: ③確認→SC UL。修正後は **1-② 提出xlsxを作り直す（修正後・Agent依頼文）**

**メール②のおすすめ文面要素（§9準拠）**:
- 目的: 「〇日開始の公式Saleの数量を見直すか」  
- 現状: ASIN／スケジュール／SC登録数量（分かれば）／シート `販売商品数_確定`  
- 再計算案: `revise_b_qty` の新旧比較  
- 手順: Deal編集→数量入力→編集内容を送信→画面で反映確認  
- 選択肢: **改定する／このまま／参加見送り**

**1回登録だけで足りる場合**: 開始が近く数量が既に固いとき。それでも **14日前メールは出す**（確認だけでも可）。

**やらないこと**:
- 期間未確定（日付なしの名付きだけ）での本登録  
- **スケジュール候補に無いイベント名をセルに書いて強制UL**（カタログにBFがあっても、当該商品のドロップダウンに無ければ不可）  
- 月枠・カスタムを公式Bとして早期UL  
- 数量改定を再バルクULに頼る  

**数量改定の反映手段**: **SCのDeal編集画面が正**（再バルクULは新規参加向きで、既スケジュールの数量は更新されないことが多い・2026-08-11確認）。

### 10.9.2 BF／イベント別提出xlsxの生成タイミング

| 条件 | 内容 |
|------|------|
| **提出してよい時** | ②推奨xlsxの**当該商品のスケジュール列ドロップダウンに、そのイベント名（日付付き）が出ている**とき |
| カタログにBFがあっても | 商品行のドロップダウン候補にBFが無ければ **まだ作れない／出すべきでない** |
| コマンド | 候補出現後に `python build_submit_xlsx.py --write --event bf` |
| 早期割引 | 候補が出てから **2026-09-30まで**に申請＋スケジュール。候補が9/30直前まで出ない場合は割引を逃す可能性あり→SCで定期確認 |
| 検知 | sync／`ops_status` で「対象ASINの候補にイベントが載ったか」を監視（実装はテンプレのスケジュール列・データ検証リスト） |

**独自セールと公式の衝突**: 後から名付き公式が台帳に載り期間が重なった場合、**名前なし（カスタム／月）側の開始・終了を短縮（または見送り）**し、`[amazonタイムセール] 独自セール日時調整（公式と衝突）` を通知する。SC側は必要なら画面編集。

自動では「日付が来たら勝手に③へ出力」しない。**候補出現を人が（または検知後にAgentが）確認してから** build する。

### 10.10 ポイント付与（Phase0＝タイムセール／Phase1＝全商品メモ）

#### 10.10.1 Phase0（確定・実装対象）— `タイムセール_マスタ` のみ

| 項目 | 内容 |
|------|------|
| 正本 | `タイムセール_マスタ`（有効行のみ） |
| 列 | `期間中ポイント%`／`期間中ポイント円`／`セール前ポイント%`／`セール前ポイント円`／`出品者ポイント現在%`／`出品者ポイント現在円`／`ポイント状態`／`ポイントメモ` |
| **期間中ポイント%** | タイム期間中の**出品者**付与率。未記入＝**1%**（シート上は可能な限り `1` を明示）。なしは明示0 |
| **期間中ポイント円** | 期間中の付与ポイント相当額（数値のみ。単位は列名の「円」） |
| **セール前ポイント%** | **最終終着%**（減衰フロア。例: API 1%）。**restore 先ではない**。`points_fetch` で上書きしない。空なら減衰フロアは **1%** |
| **セール前ポイント円** | セール前の付与ポイント相当額（数値のみ） |
| **出品者ポイント現在%／円** | 直近フィード反映後の出品者付与（%と円） |
| **ポイント状態**（語彙固定・P0-G7） | 下表のみ。空セル＝未設定。旧「セール前へ復元済」は「セール前復元済」と同義 |
| 反映本線 | SP-API Feeds `POST_FLAT_FILE_OFFER_POINTS_PREFERENCE_DATA` |
| モード | `points_send.py --mode apply`（期間中）／`--mode restore`（**減衰中%**へ戻す） |
| dry_run | 既定。TSVのみ |
| 本番 | `--prod --i-confirm-prod` ＋ `allow_prod`。任意 `--wait`／`--update-sheet` |
| SC | 本線にしない（確認用） |
| 対象外（Phase0） | 店頭合計％の取得、全カタログ、祭り自動boost |

**ポイント状態（正）**:

| 値 | いつ書く |
|----|----------|
| （空）／`未設定` | 未操作。空のままでよい |
| `セール前退避済` | 旧: fetch で終着を埋めた直後。現行 fetch は現在%のみ（終着は人手／既定1%） |
| `期間中適用済` | `points_send --mode apply` が DONE（または未wait）で `--update-sheet` |
| `セール前復元済` | `points_send --mode restore` が DONE（または未wait）で `--update-sheet`。**意味は減衰中%へ戻した**（最終終着%へ一気に戻した、ではない。語彙名は互換のため据え置き） |
| `フィード{STATUS}` | wait中／非DONE（例: `フィードIN_PROGRESS`／`フィードFATAL`） |

**フロー**:
```text
開始前: points_fetch --write で 出品者ポイント現在% をスナップ（最終終着%は触らない）
期間中: --mode apply で期間中%（既定1）を送信 → 付けすぎ防止
終了後: taper_send --poll でカレンダー同期 → --mode restore で 減衰中% へ戻す
```

**取得（P0-G9）**: `points_fetch.py` 本線は Listings Items GET の `offers[].points.pointsNumber` と `price` から `% ≈ round(pts*100/price)`（B2C優先）。`--write` 時は `出品者ポイント現在%`／円のみ同期。**最終終着%（セール前列）は埋めない**（店頭1%で終着を潰さない）。GETフィード `GET_FLAT_FILE_OFFER_POINTS_PREFERENCE_DATA` は環境により HTTP 400 のため任意フォールバック。店頭合計％は使わない。

**注意**: 店頭「986pt（22%）」はAmazonキャンペーン等を含む合計表示になりうる。退避・復元の正は**ポイントセントラルの出品者付与%**。

**コマンド**:
```text
cd tools/amazon_deals_bulk
python points_fetch.py --write
python points_send.py --backup-before
python points_send.py --mode restore
# 承認後
python points_send.py --prod --i-confirm-prod --wait --update-sheet
python points_send.py --mode restore --prod --i-confirm-prod --wait --update-sheet
```

レーンA（`discounted_price`）や Deals バルクxlsxではポイントは付かない。

#### 10.10.1b ポイントリマインド（P0-G2／G3）

日程の**自動 apply／restore は持たない**（G2）。代わりに開始／終了に合わせた**リマインドメール**（G3）で人手実行を促す。

| 項目 | 内容 |
|------|------|

| 件名 | `[amazonタイムセール] ポイント apply 確認 （期間中%送信）`／`… restore 確認 （セール前%へ戻す）` |


#### 10.10.1c 施策連動対象（P0-G4）

`points_send` の既定は **マスタ有効全件ではなく**、施策 `タイムセール` レーンBに紐づくSKUのみ。

| mode | 対象 |
|------|------|
| apply | 開始まで残り **0..`--within-days`**（既定1）または **実施中** |
| restore | 終了から **0..`--within-days`** 日経過 |

解除: `--all-master`（従来の有効マスタ全体）／`--sku`（1SKU指定時は施策連動オフ）。

```text
python points_send.py --mode apply --within-days 1
python points_send.py --mode restore --within-days 1
```

### 10.12 実質戻し（最終売価固定 ＋ ポイント減衰）

**方針**（2026-08-12 確定）:
- **タイムセールの見た目（赤札）はレーンBのみ**
- **最終売価（`目標売価円`＝our_price）は原則固定**。必要なら B 後に目標へ **一発スナップ**（段階上げしない）
- **`販促売価円` 列は削除**（使わない）
- 実質の安さは **販促ポイント%** で出し、スケジュールで **ポイント%を減衰**してセール前%へ戻す
- お客さま体感: 実質価格 ≒ 最終売価 − ポイント相当円

**減衰スケジュールの管理場所**: すべて **`タイムセール_マスタ`** の列（下記）。GAS提案／`price_recovery_*` が読む。

**人が必須入力する列（2つだけ）**:

| 列 | 例 | 意味 |
|----|-----|------|
| `目標売価円` | 4480 | 最終売価（our_price） |
| `販促ポイント%` | 22 | 減衰開始の出品者付与% |

**自動表示（シート数式）**:

| 列 | 計算 |
|----|------|
| `販促ポイント円` | `ROUND(目標売価円×販促ポイント%/100,0)`（例: 986） |
| `実質価格円` | `目標売価円−販促ポイント円`（例: 3494） |

**提案で埋まる列**（人が調整可・マスタ上で管理）:

| 列 | 例 | 意味 |
|----|-----|------|
| `減衰期間` | 3か月 | 全体の目安期間 |
| `減衰段%` | 3 | 1回に下げるポイント%ポイント（旧名「戻し価格円」）。**プルダウンなし・数値** |
| `減衰間隔` | 2週間 | 実行間隔（プルダウン） |
| `減衰開始日` | 2026-08-14 | カレンダー1段目の日付（人入力。例: 現行TS終了翌日） |
| `減衰中ポイント%` | 22→18→… | **運用目標%**（カレンダー位置。B中も進む。店頭スナップとは別） |
| `次回減衰後%` | 19 | 数式: `MAX(セール前%, 減衰中%−段%)` |
| `減衰進捗` | （ライブ文言） | 例: `進行中｜19%→16%｜終着1%｜次回09-18`（提案時は未開始サマリ可） |
| `減衰状態` | 未開始 | 未開始／進行中／完了／停止 |
| `現在売価円` | 4480 | ＝最終売価（スナップ後の確認用） |
| `次回減衰日` | YYYY-MM-DD | 実行成功時（初回は開始時） |
| `最終減衰実行日時` | ISO | 監査。実行成功時 |

**店頭の実体（ポイントブロック・読取）**: `出品者ポイント現在%`（`points_fetch`／send後 `--update-sheet`）。減衰UIと並べて人が照合する。

**終着（フロア）**: `セール前ポイント%`＝最終終着%（例: 1%）。空なら 1%。**restore 先ではない**。

**GAS都度提案**:
1. 人が `目標売価円`・`販促ポイント%` を入力
2. メニュー **6.** 新しいSKUに、何日かけて何%ずつ下げるかを記入する（選択行）
3. 確認 → 期間・段%・間隔・進捗・状態を書き込み（円・実質は数式のまま）

**提案式**（`price_recovery_logic.propose_points_taper`／GAS同式）:
- 間隔 標準 **2週間**
- 期間は販促%の大きさから（標準帯 **3か月**）
- 段% = max(1, round((販促% − 終着%) / 段数)) → **`減衰段%`** 列に格納

**CLI（現行＝計画／スナップ。減衰本番は §10.14）**:
```text
cd tools/amazon_deals_bulk
python price_recovery_send.py --start          # 減衰1段の計画 dry_run
python price_recovery_send.py --snap --sku "…" # 売価スナップ dry_run
python price_recovery_send.py --snap --sku "…" --prod --i-confirm-prod --update-sheet
```

**B期間中**: Amazon 減衰フィード・売価スナップは禁止。**カレンダー上の `減衰中%` は進める**（シートのみ。店頭は期間中1%のまま）。解除 `--allow-during-b`。

参考: [MEMO_POINTS_VS_REFERENCE_PRICE.md](MEMO_POINTS_VS_REFERENCE_PRICE.md)（ポイントは過去価格を汚しにくい）。

ヘッダ色は §2.2（実質戻しブロック=琥珀）。メニュー **99-③** ヘッダ色・入力黄・計算式を付け直す で再適用可。

#### 10.14.2 実行ロジック（1段）

