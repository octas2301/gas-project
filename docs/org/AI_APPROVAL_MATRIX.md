|------|------|

## 1. 承認UI（共通）

| 項目 | 方針 |
|------|------|
| 既定 | **GAS Web アプリ**（メール内リンク）。**Google アカウント限定**ログイン |
| 代替 | 操作性が悪い場合 **LINE** も可（施設 LINE との役割分離は実装時に決める） |
| 通知 | 失敗・要対応は **メール必須** |
| バッチ有効 | **(C) 明示取消まで有効**。実行直前に再チェック必須 |

### 実行前再チェック（最低限）

- バッチ取消フラグが立っていない  
- 対象が承認リスト（または相当）に含まれる  
- 必須項目（価格・識別子・必要な画像等）が空でない  
- 既に販売中（意図しない在庫>0）の扱いはスキップまたは別承認

## 3. 出品バッチと補充バッチの分離

```text
[承認① 朝] 在庫0/1で掲載してよい SKU 群
    → [日中] 三モール掲載（買えない／または在庫1フォールバック）
    → [12:00前] 完了目標・失敗はリトライ2回→ログ＋メール
    → [12:00〜13:00 / 夜] 確認

[承認②] 補充してよい SKU 群
    → 在庫数 = FLOOR(仕入数 ÷ セット数) をセットSKUごとに反映
    → Yahoo: setStock のみ（将来）／楽天: 在庫更新／Amazon: 在庫バルク
```

補充の換算例: 仕入バラ 30、セット数 3 → 在庫 **10**（切捨て）。

## 4. モール別・在庫掲載方式（注記＋要検証）

| モール | 掲載（在庫0/1）の想定手段 | 補充の想定手段 | 要1SKU実機検証 |
|--------|---------------------------|----------------|----------------|
| **Yahoo!** | マスタ「在庫数」を0（または1）にして既存 `runYahooExport` 相当（`setStock` が quantity を送る） | 在庫数更新後 **`setStock` のみ** | ページ表示の有無、購入不可か |
| **楽天** | 在庫数列0（または1）で既存 CSV 経路 | 在庫更新 CSV／既存反映 | 0がエラー／非表示／購入不可のどれか。不可なら **販売停止 → 極端価格** |
| **Amazon** | 自己発送の **在庫0/1バルク**（現状は手入力） | 在庫更新バルク | 見え方・カート可否。バルク列仕様は実装前に確定 |

運用者の主眼はマスタ **在庫数**。未出品との混同を避けるため、システムは **出品済ID（Yahoo等）＋在庫** でも状態を持つ（任意で「出品状態」列を後続追加）。

希望: **自分が確認できればよい**。客から見えるが買えないが理想。

## 5. SLA・リトライ

| 項目 | 値 |
|------|-----|
| 日中出品完了目標 | **原則 12:00 まで**（昼休み 12:00〜13:00 に確認可能） |
| API／ジョブ失敗 | **自動リトライ最大2回** → ログに原因追及可能な情報 → **メール必須** |
| ロールバック優先 | **出品データは消さない**。在庫を付けない／補充しない |

件数過多で12:00に間に合わない場合は、承認件数上限または25分分割ジョブ（既存 GAS 実行制限対策）を Lv 別プランで定義する（本表では注記のみ）。
