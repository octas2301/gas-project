### Amazon D 手動本線の当面特則（2026-07-30）

- 社長が子SKU行へ手動で付けた `出品CK` を、**Amazon D 手動実行に限り承認①相当**とする
- 新規カタログ／既存相乗りを同時選択可。`フル → Amazon` でも相乗りprod可
- 相乗りprodは主トグル＋`ALLOW_PROD`＋確認ダイアログ必須。フル時は楽天／Yahoo開始前に確認を完了する
- AIのレ点自動付与、無人D実行、日中トリガー接続の前にWeb承認①を再接続・再検収する
- 承認①のコード・メニュー・履歴は温存。承認②・在庫>0更新は本特則の対象外

正本: [LV4_AMAZON_CHECKBOX_MAINLINE_SELLER_SKU_APPROVAL.md](LV4_AMAZON_CHECKBOX_MAINLINE_SELLER_SKU_APPROVAL.md)

### 実行前再チェック（最低限）

- バッチ取消フラグが立っていない  
- 対象が承認リスト（または上記Amazon D特則の人間レ点）に含まれる
- 必須項目（価格・識別子・必要な画像等）が空でない  
- **マスタに該当行／SKUが無い** → 実行対象から除外し、残リスト画面にも出さない（ORPHAN扱い）  
- 既に販売中（意図しない在庫>0）は **原則スキップ**（社長決定 2026-07-15。意図した補充は承認②のみ）  
  - **レ点**＝候補選択。**スキップ**＝承認①実行時に販売中・在庫>0へ出品登録しないこと（2026-07-17確認）  
  - **販売中の情報上書き修正**は当面 **手動メニュー**（無人①の対象外。更新バッチは後続・U1）  
- 紐づけは **parentSku / childSku（＋mall）優先**（`masterRow` は補助。行削除・挿入ずれ対策）  

### 聖域（実装時の固定制約）

- 楽天: `generateRakutenCSV` を中心とする完成経路は原則 **非改変**  
- Yahoo: **`Yahoo.js` 経由のみ**（楽天経路と混ぜない）  
- B統合: 日中出品ジョブは **`B_INTEGRATED_STEP_FUNCTIONS` の順序・境界を変えない**  
- シークレット: コード／git に入れない（[AGENTS.md](../../AGENTS.md) §2）

## 3. 出品バッチと補充バッチの分離

```text
[承認① ハイブリッド: 軽い確認／一括OK可・当面社長のみ]
  在庫0/1で掲載してよい SKU 群（在庫1は画面明示 or 別承認）
    → [日中] 自動サブバッチで三モール掲載（買えない／または在庫1フォールバック）
    → [12:00前] 完了目標。失敗は失敗側のみ最大2回リトライ→ログ＋メール。成功分は再実行しない
    → [12:00〜13:00 / 夜] ページ確認・修正指示（上書きは当面手動 U1）

[承認② 別ゲート・本命ハンコ寄り] 補充してよい SKU 群（承認①とは独立。夜確認帯でも可）
    → 在庫数 = FLOOR(仕入数 ÷ セット数) をセットSKUごとに反映
    → Yahoo: setStock のみ（将来）／楽天: 在庫更新／Amazon: 在庫バルク
```

補充の換算例: 仕入バラ 30、セット数 3 → 在庫 **10**（切捨て）。

## 4. モール別・在庫掲載方式（注記＋要検証）

| モール | 掲載（在庫0/1）の想定手段 | 補充の想定手段 | 要1SKU実機検証 |
|--------|---------------------------|----------------|----------------|
| **Yahoo!** | マスタ「在庫数」を0（または1）にして既存 `runYahooExport` 相当（`setStock` が quantity を送る） | 在庫数更新後 **`setStock` のみ** | ページ表示の有無、購入不可か |
| **楽天** | 在庫数列0（または1）で既存 CSV 経路 | 在庫更新 CSV／既存反映 | 0がエラー／非表示／購入不可のどれか |
| **Amazon** | 自己発送の **在庫0/1バルク**（現状は手入力） | 在庫更新バルク | 見え方・カート可否。バルク列仕様は実装前に確定 |

**判定不能時のフォールバック順（固定）**: 在庫0試み → **在庫1** → **販売停止** → **極端価格**（先に進む条件は1SKU実機後に運用確定。順だけは変えない）。

運用者の主眼はマスタ **在庫数**。未出品との混同を避けるため、システムは **出品済ID（Yahoo等）＋在庫** でも状態を持つ（任意で「出品状態」列を後続追加）。

希望: **自分が確認できればよい**。客から見えるが買えないが理想。

## 5. SLA・リトライ

| 項目 | 値 |
|------|-----|
| 日中出品完了目標 | **原則 12:00 まで**（昼休み 12:00〜13:00 に確認可能） |
| GAS 実働（本PJ日中出品） | **約25分**で中断→トリガー再開（**課金枠30分前提**。やめる予定なし。社長決定 2026-07-17） |
| API／ジョブ失敗 | **自動リトライ最大2回**（**失敗側のみ**）→ ログ → **メール必須** |
| 部分成功 | 成功モール／成功SKUは再実行しない |
| ロールバック優先 | **出品データは消さない**。在庫を付けない／補充しない |
| 冪等 | バッチID単位の実行済み管理。明示取消まで有効でも成功済みは重複出品しない |

### 実行分割の仮既定（U2・社長決定 2026-07-17）

人が「何品番まで出すか」を判断しなくてよいように、**実行エンジンが自動分割**する。

1. **楽天画像アップ 50枚優先**: サブバッチは **ユニーク画像数 ≤ 50** で切る（共有サブ画像は1枚カウント）。品番数の固定上限（例: 2品番）は必須としない。  
2. **時間**: 上記サブバッチを順に実行し、経過が **約25分**に達したら中断→レジューム。  
3. **12:00未完了**: 未消化はキューに残し **翌朝続き**（明示取消まで有効と整合）。  

無料枠向けの「5分30秒」は **本PJ日中出品ジョブの既定にしない**（一般GAS注意・他環境用）。実測後の数値チューニングは可（切り方の優先順位は変えない）。
