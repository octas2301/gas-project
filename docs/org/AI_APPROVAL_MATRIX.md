## 1. 承認UI（共通）

| 項目 | 方針 |
|------|------|
| 既定 | **GAS Web アプリ**（メール内リンク）。**Google アカウント限定**ログイン |
| 代替 | 操作性が悪い場合 **LINE** も可（施設 LINE との役割分離は実装時に決める） |
| 承認権限 | **当面は社長のみ**（後で社員拡張可）。社長決定 2026-07-15 |
| 通知 | 失敗・要対応は **メール必須** |
| バッチ有効 | **(C) 明示取消まで有効**。実行直前に再チェック必須。**同一バッチの成功済みは再実行しない**（冪等） |

### 実行前再チェック（最低限）

- バッチ取消フラグが立っていない  
- 対象が承認リスト（または相当）に含まれる  
- 必須項目（価格・識別子・必要な画像等）が空でない  
- 既に販売中（意図しない在庫>0）は **原則スキップ**（社長決定 2026-07-15。意図した補充は承認②のみ）  
  - **レ点**＝候補選択。**スキップ**＝承認①実行時に販売中・在庫>0へ出品登録しないこと（2026-07-17確認）  
  - **販売中の情報上書き修正**は当面 **手動メニュー**（無人①の対象外。更新バッチは後続・U1）  

### 聖域（実装時の固定制約）

- 楽天: `generateRakutenCSV` を中心とする完成経路は原則 **非改変**  
- Yahoo: **`Yahoo.js` 経由のみ**（楽天経路と混ぜない）  
- B統合: 日中出品ジョブは **`B_INTEGRATED_STEP_FUNCTIONS` の順序・境界を変えない**  
- シークレット: コード／git に入れない（[AGENTS.md](../../AGENTS.md) §2）

## 3. 出品バッチと補充バッチの分離

```text
[承認① 朝・当面社長のみ] 在庫0/1で掲載してよい SKU 群（在庫1は画面明示 or 別承認）
    → [日中] 三モール掲載（買えない／または在庫1フォールバック）
    → [12:00前] 完了目標。失敗は失敗側のみ最大2回リトライ→ログ＋メール。成功分は再実行しない
    → [12:00〜13:00 / 夜] 確認

[承認② 別ゲート] 補充してよい SKU 群（承認①とは独立。夜確認帯でも可）
    → 在庫数 = FLOOR(仕入数 ÷ セット数) をセットSKUごとに反映
    → Yahoo: setStock のみ（将来）／楽天: 在庫更新／Amazon: 在庫バルク
```

補充の換算例: 仕入バラ 30、セット数 3 → 在庫 **10**（切捨て）。

## 4. モール別・在庫掲載方式（注記＋要検証）

| モール | 掲載（在庫0/1）の想定手段 | 補充の想定手段 | 要1SKU実機検証 |
|--------|---------------------------|----------------|----------------|
| **Yahoo!** | マスタ「在庫数」を0（または1）にして既存 `runYahooExport` 相当（`setStock` が quantity を送る） | 在庫数更新後 **`setStock` のみ** | ページ表示の有無、購入不可か |
| **楽天** | 在庫数列0（または1）で既存 CSV 経路 | 在庫更新 CSV／既存反映 | 0がエラー／非表示／購入不可のどれか |
| **Amazon** | 自己発送の **在庫0/1バルク**（現状は手入力） | 在庫更新バルク | 見え方・カート可否。バルク列仕様は実装前に確定 |

**判定不能時のフォールバック順（固定）**: 在庫0試み → **在庫1** → **販売停止** → **極端価格**（先に進む条件は1SKU実機後に運用確定。順だけは変えない）。

運用者の主眼はマスタ **在庫数**。未出品との混同を避けるため、システムは **出品済ID（Yahoo等）＋在庫** でも状態を持つ（任意で「出品状態」列を後続追加）。

希望: **自分が確認できればよい**。客から見えるが買えないが理想。

## 5. SLA・リトライ

| 項目 | 値 |
|------|-----|
| 日中出品完了目標 | **原則 12:00 まで**（昼休み 12:00〜13:00 に確認可能） |
| API／ジョブ失敗 | **自動リトライ最大2回**（**失敗側のみ**）→ ログ → **メール必須** |
| 部分成功 | 成功モール／成功SKUは再実行しない |
| ロールバック優先 | **出品データは消さない**。在庫を付けない／補充しない |
| 冪等 | バッチID単位の実行済み管理。明示取消まで有効でも成功済みは重複出品しない |

### 12:00超過時の既定候補（未決・空欄禁止）

Lv 別プランで1つを既定にする。候補は次を列挙したまま残す:

1. **承認件数上限**（朝のバッチサイズ制限）  
2. **時間分割／オートレジューム**（GAS 実行制限対策。25分分割または 5分30秒中断再開など）  
3. **翌朝再実行**（未完了分）
