# Lv別実装プラン（叩き台）

**文書種別**: 実装ロードマップ（叩き台・コードなし）  
**最終更新**: 2026-07-17  
**親文書**: [AI_ORG_CHARTER.md](AI_ORG_CHARTER.md) ・ [AI_APPROVAL_MATRIX.md](AI_APPROVAL_MATRIX.md) ・ [PHASE0_THREE_REVIEW_MAJORITY.md](PHASE0_THREE_REVIEW_MAJORITY.md)  
**前提**: Phase0 の憲章・マトリクス・多数決は docs 済み。**社長による多数決メモ最終承認**のあと、本プランを確定版に昇格させる。  
**本ドキュメント時点**: **実装コードは書かない**（方針と着手順の正本化）。

---

## 1. 目的

朝モバイル承認 → 日中無人出品（原則12:00前）→ 夜確認、を **壊さず段階導入**する。  
一度に三モール＋承認UI＋補充を作らず、**検収できる単位（Lv）**で進める。

---

## 2. 全Lv共通の固定制約（聖域）

| 制約 | 内容 |
|------|------|
| 楽天 | `generateRakutenCSV` を中心とする完成経路は原則 **非改変**。日中ジョブは既存関数の **呼び出しラッパー**に留める |
| Yahoo | **`Yahoo.js` のみ**。楽天経路と混ぜない。出品対象は **子SKUのレ点**のみ |
| B統合 | `B_INTEGRATED_STEP_FUNCTIONS` の **順序・境界を変えない** |
| シークレット | コード／git に入れない |
| 承認 | 当面 **社長のみ**。不可逆は要承認。CS／問屋の **自動送信禁止** |
| 在庫 | 掲載は **0原則**（不可なら1・画面明示または別承認）。販売中(在庫>0)は **原則スキップ**。補充は承認② |
| 冪等 | 同一バッチの成功済みSKUは再出品しない。部分成功は失敗側のみ最大2回リトライ |
| clasp | 自動 `clasp push` は当面禁止（人間） |

詳細は憲章・マトリクス・[AGENTS.md](../../AGENTS.md) §2。

## 3. Lv一覧（推奨順）

| Lv | 名前 | ゴール（検収一文） | コード有無 |
|----|------|-------------------|------------|
| **0** | Phase0 クローズ | 社長が多数決メモを最終承認し、未決の扱い（先送り／決定）が文書上はっきりしている | なし |
| **1** | 承認キュー骨格 | 朝に「今日実行してよいSKU一覧」をモバイルで承認／取消でき、承認結果がシート（または相当）に残る。**出品APIはまだ呼ばない** | あり（GAS Web＋シート） |
| **2** | Yahoo 日中掲載（在庫0/1） | 承認①済み・子レ点のみを、日中に Yahoo 既存経路で掲載／在庫0or1。12:00前完了目標・冪等・失敗メール | あり（`Yahoo.js` 呼出中心） |
| **3** | 楽天 日中掲載（在庫0/1） | 承認①済みを既存楽天CSV／反映経路で掲載（**聖域内**）。Yahoo と同一バッチIDで追跡可 | あり（既存メニュー／関数のオーケストレーションのみ） |
| **4** | Amazon バルク掲載（在庫0/1） | 承認①済みを Amazon 在庫0/1バルクで掲載。手入力脱却の最小版 | あり（要列仕様確定） |
| **5** | 補充バッチ（承認②） | 夜または承認後に `FLOOR(仕入÷セット)` で販売可能数へ。出品データは消さない。Yahoo は setStock 優先を目指す | あり |
| **P** | 並行トラック | 本線を止めない周辺（下記 §5） | まちまち |

Lv2→3→4 のモール順は **既存完成度（Yahoo分離済み・楽天聖域・Amazon手作業）** を優先した叩き台。社長判断で **楽天を先**に入れ替え可（その場合も聖域は不変）。

## 4. 各Lvの詳細

### Lv0 — Phase0 クローズ

| 項目 | 内容 |
|------|------|
| 成果物 | [PHASE0_THREE_REVIEW_MAJORITY.md](PHASE0_THREE_REVIEW_MAJORITY.md) のチェック完了＋本プランの「確定」注記 |
| 着手条件 | 多数決メモ・憲章・マトリクスが remote にある（済） |
| 完了条件 | 社長が「多数決メモを最終承認した」と明示。未決表の先送りが許容されている |
| やらない | 実装コード |

### Lv1 — 承認キュー骨格（出品なし）

| 項目 | 内容 |
|------|------|
| 成果物 | GAS Web（Googleログイン）承認画面／または同等のモバイル承認導線。承認①バッチID・SKUリスト・取消・在庫0/1明示 |
| 着手条件 | **Lv0 完了** |
| 完了条件 | 社長が電車で承認→シートに残る→取消が効く。**外部ECへの書込ゼロ** |
| 依存 | 対象SKUの抽出元（マスタのレ点／候補列）を要件で固定 |
| リスク | UX不良→LINE代替は未決のまま残してよい（マトリクスどおり） |
| やらない | `editItem` / `setStock` / 楽天反映 / Amazon バルク |

### Lv2 — Yahoo 日中掲載

| 項目 | 内容 |
|------|------|
| 成果物 | 承認①＋日中トリガー（または手動キック）で Yahoo 掲載。ログに runId／バッチID／SKU／state |
| 着手条件 | Lv1 完了。既存 Yahoo 出品が手動メニューで安定していること |
| 完了条件 | テスト少数SKUで在庫0（または明示1）掲載成功。販売中スキップ。冪等確認。12:00超過時は §6 の選択肢から運用を1つ仮決め |
| 未決の扱い | Yahoo **新規**（it-07004 手動反映）を日中バッチから分離するか → 未決のままなら **既存更新のみ**で Lv2 を閉じる |
| やらない | 楽天CSV改変、B統合 Step 並べ替え、親だけレ点で全子出品 |

### Lv3 — 楽天 日中掲載（聖域内）

| 項目 | 内容 |
|------|------|
| 成果物 | 同一承認①バッチを楽天既存経路で実行するオーケストレーション |
| 着手条件 | Lv2 でバッチ追跡の型が固まっていること（または Lv1＋楽天手動経路の安定） |
| 完了条件 | テストSKUで在庫0/1掲載。`generateRakutenCSV` 本体に差分を入れない（ラッパー／メニュー呼び出しのみ） |
| やらない | CSV生成ロジックの書き換え、FTP仕様変更 |

### Lv4 — Amazon バルク

| 項目 | 内容 |
|------|------|
| 成果物 | 在庫0/1掲載バルクの最小運用（列仕様・ファイル置き場・承認①連携） |
| 着手条件 | Lv1 完了＋Amazon 列仕様の社長確認（多数決未決の消化） |
| 完了条件 | 手入力より短い手順でテスト出品できる。失敗はログ＋メール |
| 未決 | Seller Central 手動 vs 半自動の最終手段 → Lv4 着手前に決定 |

### Lv5 — 補充（承認②）

| 項目 | 内容 |
|------|------|
| 成果物 | 承認②リストに対し `FLOOR(仕入÷セット)`。セット数≤0 は補充停止＋ログ＋メール（推奨案） |
| 着手条件 | Lv2〜4 のいずれかで「掲載済みSKU」が安定して識別できること |
| 完了条件 | 補充後も出品データが消えない。意図しない在庫>0 スキップと矛盾しない |
| やらない | 承認①とゲート混同、CS送信自動化 |

## 6. 未決の置き場（多数決メモからの引き継ぎ）

| 未決 | 閉じるLv | 仮運用（閉じるまで） |
|------|----------|----------------------|
| 在庫1販売時のキャンセル／返金 | Lv5以降／CS | 人が手動。自動送信しない |
| Yahoo 新規を日中分離するか | Lv2 | 既存更新のみで進める |
| `セット数≤0` | Lv5 | 補充停止＋ログ＋メール |
| Amazon バルク最終手段・列仕様 | Lv4 着手前 | 手入力継続 |
| LINE と施設 LINE の権限分離 | Lv1 実装時 | GAS Web 既定 |
| 12:00×件数上限・オートレジューム | Lv2〜3 実測後 | 件数上限／分割／翌朝再実行から社長が1つ選ぶ |
| 補充と flowchart 表記 | 任意 | マトリクス§3を正 |
