## 1. スコープ

### 1.1 作るもの

| # | 成果物 |
|---|--------|
| 1 | 承認キュー（`▼承認キュー(出品①)`）から **mall=`rakuten` かつ lineStatus=`APPROVED`** を読む入口 |
| 2 | 実行サブバッチ分割（**ユニーク画像 ≤ 50**／経過 **約25分**で中断→レジューム） |
| 3 | マスタ上の出品対象合わせ（承認済み親SKUにレ点が付いている状態で既存CSVを呼ぶ／または同等の一時スコープ） |
| 4 | 在庫0（既定）／在庫1（バッチ `inventoryMode=ONE` のみ）の **掲載前マスタ在庫の扱い**（書込範囲を明示） |
| 5 | `runId` / `batchId` / `subBatchId` / SKU / `state` の調査ログ＋失敗メール |
| 6 | メニューまたは時間トリガーからの **手動キック／日中キック**（Lv2はまず手動でも可） |

### 1.2 作らないもの（禁止）

- `generateRakutenCSV` 内部ロジックの書き換え（列マッピング・Shift-JIS・FTPペイロード等）  
- MAKE シナリオ仕様の変更（既存 Webhook を呼ぶだけ）  
- Yahoo / Amazon の実行  
- 承認②（補充）・販売中SKUへの無人上書き（U1）  
- B統合 `B_INTEGRATED_STEP_FUNCTIONS` の順序・境界変更  
- マスタへのジャンル自動登録  
- `clasp push` 自動化  

### 1.3 聖域の守り方

```text
[Lv2 ラッパー]
  → 承認済み楽天SKUに対象を絞る（レ点／一時フィルタ）
  → 在庫0/1をマスタの楽天在庫列へ必要最小だけ合わせる（要実装設計・承認）
  → generateRakutenCSV(skipConfirm=true, ssOverride=...) を呼ぶ
  → （既存どおり）Drive保存 → MAKE → 反映確認 → 完了メール
```

既存の一括出品（`コード.js` 内の楽天CSV→Yahoo）は **触らない**。Lv2は承認キュー起点の別エントリとする。

## 3. 入力・対象SKU

### 3.1 承認キュー

- シート: `▼承認キュー(出品①)`（Lv1）  
- 対象: ヘッダ `status=APPROVED` かつ明細 `mall=rakuten` かつ `lineStatus=APPROVED`  
- `REJECTED` / `CANCELLED` / `ORPHANED` は実行しない  
- 実行直前再チェック: マスタに親SKUが無い → ORPHAN扱い・スキップ（方式A）  
- 販売中かつ在庫>0 → **原則スキップ**（承認①の掲載対象外。補充は②）

### 3.2 楽天の行単位

- Lv1抽出どおり **親行**（子SKU空＋出品CK運用）。  
- `generateRakutenCSV` は従来どおりマスタの **出品CK** を見るため、ラッパーは次のいずれか（実装時に1つ選ぶ・要承認）:

| 案 | 内容 | 利点 | リスク |
|----|------|------|--------|
| **A（採用 2026-07-19／親子レ点に修正 2026-07-20）** | 実行直前に「承認済み親＋**同一親SKUの子行**をレ点ON／他はOFF」のスナップショットを取り、CSV実行後にレ点を復元。通常の手動出品（親子レ点）と同じ形にし、`generateRakutenCSV` をマルチSKU経路へ乗せる | 聖域関数を変えずに対象限定。バリエーション商品でも32バイト超過（親だけレ点→シングルSKU扱い）を避ける | レ点の一時変更（マスタ操作）。失敗時復元必須 |
| **B** | 人間が既にレ点した集合 ⊆ 承認済み、のみ実行（承認外レ点はエラーまたはスキップ） | マスタを触りにくい | 運用がレ点と承認の二重管理 |

**採用は A（親子一時レ点）**。復元失敗時はメール必須・処理中断。  
※ 2026-07-20 以前の「親だけON」実装は、バリエーション親でシングルSKU経路に入り `SKU選択肢が32バイト超過` となり実用不可だったため修正。

### 3.3 在庫0/1

- バッチヘッダ `inventoryMode`: `ZERO`（既定）/ `ONE`  
- 掲載前に、対象親（およびCSVが参照する在庫列）を **0または1** に合わせる処理が必要なら、**対象SKUの在庫列のみ**・実行ログ必須・トグルでOFF可  
- 販売可能数への引き上げは **しない**（承認②）

## 4. 実行分割（U2仮既定の楽天適用）

詳細の正: [AI_APPROVAL_MATRIX.md](AI_APPROVAL_MATRIX.md) §5 ・多数決メモ §4.3。

| 規則 | 内容 |
|------|------|
| 画像 | サブバッチ内の **ユニーク画像数 ≤ 50**。共有サブ画像は1枚。識別子は §6 |
| 時間 | 1実行あたり実働 **約25分**で中断→Script Properties に再開位置→トリガー再開（課金30分前提） |
| 品番 | 固定2品番は必須としない。ユニーク50に収まるだけ親SKUを積む |
| 12:00 | 未完了はキュー／サブバッチ残として翌朝続き（明示取消まで有効） |
| 冪等 | 同一 `batchId`+SKU で成功済みは再CSVしない。失敗側のみ最大2回 |

`subBatchId` 例: `{batchId}_R{n}`（n=1,2,…）

## 10. 人間向け検証手順（実装後・自宅）

1. Lv1検収済みであること  
2. `git pull` → `clasp push`（本修正後は必須）  
3. Property: `APPROVAL_RAKUTEN_LV2_ENABLED=true`（初回は任意で `APPROVAL_RAKUTEN_LV2_SKIP_CSV=true`）  
4. **バリエーションあり**の楽天親を承認①（親子レ点の通常運用でOK）  
5. 19-① → ログに `childrenOn=` が出ること／32バイト超過で即落ちないこと  
6. 実行後、出品CKが実行前に戻っていること（§10.1 A）  
7. 終わったら Property を false  
8. （任意）RMS／反映ログの目視（§10.1 B）  

### 10.1 目視チェック場所（出品CK復元・RMS反映）

#### A. 出品CKが「元に戻っている」か（スプレッドシート）

「元に戻る」＝ **実行直前のレ点状態のスナップショットへ復元**（全部オフにする、ではない）。

1. シート **`▼商品マスタ(人間作業用)`** を開く  
2. 列 **`出品CK`** を見る（チェックボックス列）  
3. テスト親（例: `lifec-4560151300139-oya`）と、その親SKUが同じ **子行（子SKUが空でない行）** を探す  
4. **OKの目安**: 実行前と同じ並び（通常運用なら親＋全子にレ点が付いたまま、など）。実行中だけ一時的に他商品のレ点が外れ、終了後に戻っている  
5. **NGの目安**: 親だけONで子が全部OFF／関係ない商品のレ点が消えたまま／復元失敗メールが来ている  

#### B. RMS側の反映（任意・時間がかかることがある）

GAS側で既に「MAKE/FTP成功・反映確認 対象7件」まで出ている場合、**必須ではない**。気になるときだけ:

| どこ | 見方 |
|------|------|
| **シート `楽天反映確認ログ`** | 直近行に反映確認開始／完了・対象商品数が残っているか |
| **メール** | 「楽天反映確認」件名（全件200なら反映完了／タイムアウトなら件数付き） |
| **RMS（店舗管理画面）** | ログイン → **商品管理**（または **SKU管理**）→ 管理番号／商品番号／JAN（例 `4560151300139`）で検索 → 商品・SKUが更新されているか。在庫0掲載なら在庫が0付近か |

FTP反映は数分〜数時間かかることがある。エラー時は RMS の FTP／一括登録の結果・エラーCSVも確認する。
