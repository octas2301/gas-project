## 2. 流れとゴール

```text
本線
  A 店起点①–⑧
      → 洗うメーカーを決める
      → その店の取扱（query で取れた分）を C へ
  B メーカー洗い
      → C 倉庫（Keepa）
  D 品番リストへ転記 → 機械で絞る
  E 見積もり提案書を人にメール → 見積可のメーカーだけ
  F 見積作成（メーカーまとめ）→ 依頼メール → 送信
  G 返信確認 → 見積回答取得
  H 原価を表へ → 利益計算
  I 仕入れ提案書を人にメール → 承認品番だけ
  J 発注書 → 発注メール → 送信

分岐 A′（メーカー問屋からの仕入提案、仕入れ選定）
  書類で品を特定 → 検討する品を選ぶ
      ├ C に既にある → 同じ門
      └ 無い → 商品名／JAN → SP-API → Keepa → C → 同じ門
  D リストへ載せる
  単価あり → E・F・G を飛ばして H
  単価なし → 本線 E から
  その後 I → J
```

| 記号 | ゴール（できたと言える状態） |
|------|------------------------------|
| **A** | 店から「洗うメーカー」まで辿れる。取扱の取得結果が倉庫に残る（全SKUではない） |
| **B** | 指定メーカーの品が、門の結果付きで候補になる |
| **C** | 同じ Keepa／取扱を、洗い・品番リスト・出品が90日内使い回せる |
| **D** | 倉庫からリストへ載る。機械が候補を絞る。既存の式は流用し、必要な範囲で最適化する |
| **E** | 見積もり提案書が人に届き、見積可のメーカーだけ F に進む |
| **F** | 可とされたメーカー単位で依頼が作られ、相手に届く（人送信可） |
| **G** | どのメーカーのどの品がいくらか、機械が拾える |
| **H** | 表に原価が入り、利益が見える |
| **I** | 仕入れ提案書が人に届き、表に承認が残り、承認品番だけ J に進む |
| **J** | 承認分の発注が相手に届く（人送信可） |
| **A′** | 提案品が同じ門・同じリストに乗る。倉庫に無ければ SP-API→Keepa。単価ありなら H へ |

## 5. 受け渡し契約（2026-08-16 ロック）

各フローは **入力 → 機械 → 人（任意）→ 出力**。列字母は実装時。

|--------|------|------|----|----------------|

| **B** | メーカー名 | Catalog →（>500はタイトルからカテゴリ推定・分割語シート）→ Keepa → 門 | 推定失敗時は人。AIはGemini主 | 門付き ASIN → C と ①候補 |

### 5.4 セラー台帳へ店を足す（＝A の①）

**置き場**: 競合DB「セラー」。品番リストには書かない。

**誰を足す**: 門を通った商品について、**カート店（倉庫 Keepaフルの BuyBox列。新規 Keepa GET しない）と、新品オファーの店（SP-API）の両方**。和集合。中古は入れない。同じ sellerId は1行。

**上限**: 1回の作業で **新規100店まで**（既存は数えない）。

**Keepa を使うところ**: 属性・倉庫・店の構成比（`storefront=0`）。構成比は **その店を洗うときに1店ずつ**。この貯めでは Keepa しない。出品一覧一括（storefront=1 / Keepa offers 本線）は禁止。

**タイミング**: 門通過分をまとめて足してよい（倉庫追記直後に限定しない）。

**GAS（C0）**: メニュー「C0. セラー貯め」。`PurchaseResearch.js` `prRunSellerAccum_`／`prMenuSellerAccum`。**1回のメニュー**で新規100店または未済 ASIN 0 までループ（429 時は既定90秒待機→最大5回再試行。25分切れで停止）。①候補の門通過 ASIN のうち **`セラー調査済みSP-API` が空の行だけ** → Keepaフル `BuyBoxセラー` 列 JOIN ＋ SP-API `getItemOffers`（新品）。SP-API 成功後は当該行に **`セラー調査済みSP-API`=ON** と **`セラー調査日時`** を書く（新規 sellerId 0 でも付ける）。**新品オファーが200以外**（429以外）の ASIN は **済にして次へ**（BuyBox 店は残す）。①ログ `C0 skip_http` に `asin=` `http=` `err=` を残し、後から原因を追える。切戻し `PR_C0_SKIP_HTTP=false`（旧: 全体停止）。競合DB `セラー` 末尾に新規最大100行（`採取元=bb+spapi_new`、調査CK **OFF**）。429／25分切れ後は **未タグ ASIN から** 再実行（手動でも自動429リトライでも可）。切戻し `PR_SELLER_ACCUM_ENABLED=false`／ループ off は `PR_SELLER_ACCUM_LOOP=false`。

**背景**: 2026-10-09 以降、心拍は動くが①候補が増えない。合否は **洗い本線不合格**（§3 B）。人が同じ洗いメニューを押し直す運用は完成形にしない（全自動）。

**原因（確定）**

| # | 穴 | 証拠の型 |

| 1 | `実態=未調査`（または要確認）で洗わない skip のあと、**次の洗い／心拍を予約しない** | ①ログ `full_trigger 洗い完走` → `実態=未調査 parent=…` の直後に切片なし |
| 2 | 心拍が `washN≥1` なら生存扱いのまま **再武装しない**（死んだ予約でも沈黙に入らない） | liveness detail `washN=1 rearmed=0 reason=wash_trigger` が連日 |
| 3 | `効率合否 FAIL no_slice_stall` は **検知のみ** | CYCLE 既存。FAIL が出てもトリガーも Keepa中も直さない |
| 4 | **Keepa中＋実態未調査** の社が選定に残り得る。実態AIが `skip_same` だと実態が進まず同じ穴に戻る | メーカーサマリ／実態AIログ |

## 7. 自動化の思想（Python と GAS）

**完成形**: 出品の `コード.js` に混ぜない。①専用 GAS（`purchase_research/`）で A〜D を回す。第1版の起動は **人がメニュー**。週次などの時間トリガーは **承認後**（新設しないのが既定）。

**いま**: 手順と表の形を固めるため、同じ Keepa／Catalog／シートを **手元の Python が書いてきた**。① GAS に **メーカー洗い**（現状は Catalog page0→Keepaフル→門→①候補。スライス **cap20**）を移植済み。**完走の正**は [FULL](B_MAKER_WASH_FULL_REQUIREMENTS.md)（一時キュー列挙→Keepa完走。実装は P1〜）。無人の定期実行にはなっていない。

**GAS は手元の Python を直接叩けない。** 「Python 本線のまま GAS トリガーだけ」では自動化にならない。載せ替えは次のいずれか（今は A が正）。

| 案 | 内容 |
|----|------|
| **A（正）** | ロジックを① GAS に移植。トリガーは後 |
| B | Python をクラウドまたは PC の時計で回す（GAS トリガーは使わない） |
| C | GAS トリガーが HTTP で Python を呼ぶ（サーバが要る） |

**載せる想定でテストする（必須）**

- 正は HTTP GET（Keepa `/query`・product、Catalog）とスプレッドシートの列。Python のコマンド・ローカル JSON ファイルは **殻**。GAS では `UrlFetchApp` / `SpreadsheetApp` に置き換える
- **Keepa／Catalog はスライス**（例: Keepa 20件・店 total>1000 で当該店停止）。一気に全件ループを1実行の仕様にしない。メーカー完走は **状態を残して繰り返し**（FULL）
- Catalog の「ファイルに保存してから洗う」はテスト用。本線 GAS では検索結果を **`①洗いキュー`** に書いてから Keepa（FULL）。探索用 page0 直洗いは本線外
- 交差表 xlsx 等は①自動化の対象外

**やってはいけない**: Python でしか呼べないライブラリを本線の必須にする。出品 clasp に①を足す。トリガーを黙って新設する。
