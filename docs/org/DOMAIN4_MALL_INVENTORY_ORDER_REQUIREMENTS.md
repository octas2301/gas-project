## 1. 目的・スコープ

### 1.1 ゴール一文

実在庫（inventory-app・単品JAN）を正とし、出品マスタ子SKUごとの適正在庫を日次で算出し、Amazon（自己発送）／楽天／Yahoo! へ同じ数字で自動反映する。不足は発注点判定のうえメールし、発注書下書きまで出す。

### 1.2 やること（第1版）

| 本線 | 内容 |
|------|------|
| モール在庫取得 | 3モールの販売在庫を API で取得（FBA は取得のみ） |
| 適正在庫算出 | 実在庫−安全在庫をセット数で割り、子SKU単位の表示数を算出 |
| モール反映 | 自己発送在庫を日次で上げ下げとも自動書き込み（全モール同数） |
| 発注アラート | 月販＋リードタイムで発注点判定 → メール → 発注書下書き |

### 1.3 やらないこと（この領域・第1版）

- inventory-app の棚卸・スキャン UI／入出荷画面の改修（必要なら依存として別チャット）
- 出品本線の改修（楽天CSV生成、Amazon SP-API PUT／出品承認フロー、Yahoo 出品本体）
- リサーチ・見積・広告本線
- FBA 在庫の自動更新（Amazon 側管理。取得データは発注計算にのみ使用）
- LINE 同時配信（将来メモのみ）

### 1.4 他チャット境界

| 対象 | 本チャット | 別チャット |
|------|------------|------------|
| 領域4（同期・適正・発注） | 主 | — |
| inventory-app 本体 | 読み取り依存の明示のみ | 棚卸・UI・入出荷改修 |
| 出品 GAS（楽天／Yahoo／Amazon Lv4） | 聖域・触らない | 出品本線 |

## 3. 用語

| 用語 | 定義 |
|------|------|
| 実在庫 | inventory-app 上の単品JANの現在庫（発注・入荷と同じ粒度の単品SKU）。単位は「単品1個」（袋に限らない） |
| 販売在庫 | 各モールに表示されている販売可能数 |
| 適正在庫 | 子SKUごとにモールへ載せる目標販売在庫（全モール同数） |
| 安全在庫 | ロス・棚ずれ・未反映出荷等を見込んだバッファ（単品JAN単位） |
| セット数 | 出品マスタ子行のセット数（1セットあたり消費する単品数）。ミックスは構成×セット数で単品へ分解 |
| 子SKU | 出品マスタのセット数付き販売SKU（適正在庫のキー） |
| 自己発送 | 自社／施設発送のモール在庫。本領域が更新対象 |
| FBA | Amazon倉庫在庫。取得のみ・更新しない。発注計算の入力に使う |

## 4. データモデル（実装粒度）

### 4.1 キーと正本

| データ | キー | 正本 |
|--------|------|------|
| 実在庫 | 倉庫キー（B1: inventory-app「単品JAN」欄＝本物JANまたは社内キー） | `inventory-app` |
| 販売SKU・セット数 | 子SKU（セット数は数値セル） | 出品マスタ（▼商品マスタ 人間作業用） |
| 単品の紐付け | 代表JAN（＝その単品の倉庫キー）で可 | 出品マスタ ↔ inventory-app |
| ミックス構成 | 構成比商品一覧の**構成品JAN／社内キー**（代表JANは倉庫キーにしない） | 出品マスタ COMBO／構成列。計算は P6 |
| 薄い紐付け台帳 | stock_key 等 | 領域4専用スプシ（案A第2段）。巨大発注マスタは作らない |
| モール販売在庫（読取） | モール側SKU／出品者SKU | 各モール API |
| 適正在庫（算出結果） | 子SKU | **案A**: P0＝ローカルTSV → 領域4専用スプシ → モール／必要ならマスタ「在庫数」 |
| 月販実績 | 倉庫キー（子売上はセット数で単品換算） | 各モール実績 API |
| 発注書下書き | 倉庫キー | 本領域が生成（送信は人）。見積との揺れは台帳で後付け紐付け |

### 4.2 エンティティ関係（概念）

```text
単品JAN（実在庫）
  ├─ 安全在庫・月販・発注点（単品）
  └─ 子SKU（セット数 N）… 適正在庫 = floor(可用 / N)
       └─ 3モール自己発送へ同数反映
ミックス親
  └─ 構成単品×数量 × セット数 → 単品JAN消費に分解（COMBO約束）
```

### 4.3 依存（アプリ改修が必要になったら明示するだけ）

- inventory-app: 現在庫の安定した読取口（シート／API）。無い・不安定なら依存タスクとして別承認。
- 出品マスタ: 子SKU・セット数・JAN／構成の参照のみ。楽天CSV・出品 PUT は触らない。

## 5. フロー全体

```text
[日次]
1. 実在庫読取（inventory-app・単品JAN）
2. モール販売在庫取得（API。FBA含む取得、更新は自己発送のみ）
3. 月販平均取得（自社実績 API）→ 単品換算
4. 安全在庫・可用・子SKU適正在庫を算出
5. 3モール自己発送へ同数で上げ下げ自動反映
6. 発注点判定（残り日数＋LT）→ 該当をメール
7. 発注書下書き生成（人の送信待ち）
8. 監査ログ（差分・成功/失敗）
```

失敗時: 部分失敗を許容しログ＋メール。成功分のロールバックはしない（翌日再同期で収束）。

## 7. 適正在庫算出

### 7.1 採用方針（XとYの整理）

| 案 | 要点 | 第1版 |
|----|------|-------|
| X | 全モール同数＋安全在庫＋同時掲載の重い係数でさらに控えめ | 係数は **入れない** |
| Y | 全モール同数＋**日次で実在庫に合わせて再計算・再同期** | **本線** |

前提: 日次で合わせ直すため、よほどのことがない限り「1か月分が1日で消える」ことはない。  
よって **食い合いリスクは日次再同期（Y）で吸収**し、バッファは **安全在庫（月販×日数）のみ**とする。売り逃しを増やす二重引き（モール数割り等）は第1版では採用しない。問題が出たら係数や配分を後から足す。

### 7.2 計算式（ロック）

単品JANごと:

```text
月販_単品 = 直近の自社実績から算出した月間販売数（単品換算）
安全在庫 = 月販_単品 × (安全日数 / 30)     # 第1版の安全日数 = 7（1週間分）
可用     = max(0, 実在庫 − 安全在庫)
```

子SKUごと（セット数 N。単品シリーズ）:

```text
適正在庫_子 = floor(可用 / N)
```

ミックス（構成あり）:

```text
# 子の1セット販売に必要な単品 j の個数 = 構成数量_j × N
# その子を何セット載せられるか = 各構成単品について floor(可用_j / (構成数量_j × N)) の最小
適正在庫_ミックス子 = min_j floor(可用_j / (構成数量_j × N))
```

全モール（自己発送）へ **同じ `適正在庫_子`** を書く。

### 7.3 月販の扱い

- 元データ: 自社実績を各モール API で取得し合算（単品JANへ換算）。
- 「月販平均」の窓（何日／何か月）は実装前に仮決めし §13 でロック（当面案: 直近30日×30/実日数、または直近90日平均）。
- FBA出荷分も発注・月販に含める（在庫更新はしないが需要としては使う）。

### 7.4 端数・ゼロ

- `floor` で切り捨て。可用0なら適正在庫0。
- マスタにセット数欠損の子はスキップ＋ログ。

## 9. 発注アラート

### 9.1 発注点

```text
リードタイム LT = 14日（発注〜入荷）
カバー日数     = 安全日数(7) + LT(14) = 21日  # 解釈: 「残りが約1か月を切る」運用を、実在庫÷月販 に LT を足した発注点で実装
残日数         = (実在庫 / 月販_単品) × 30     # 月販が月あたりのとき
発注アラート   = 残日数 ≤ (30日相当の閾値) に LT を織り込込んだ判定
```

**ロックした意図の実装式（単品JAN）**:

```text
# 「実在庫÷月販」で残月を出し、LT2週間を足した必要在庫と比較
必要在庫 = 月販_単品 × ((30 + LT日数) / 30)   # 約1か月＋LT分を下回ったらアラート、に相当
# より直感的な同等式:
発注点在庫 = 月販_単品 × ((安全日数 + LT日数) / 30)
アラート条件 = 実在庫 ≤ 発注点在庫
```

すり合わせメモ: ユーザー意図は「残り約1か月を切ったら」＋「LT2週間を足す」。第1版は **発注点 = 月販×(30+14)/30（約1.47か月分）** を採用し、安全在庫（表示用の7日）と発注点を役割分担する。  
- 安全在庫7日: モール表示を抑える用  
- 発注点 ≈ 1か月+LT: 仕入れ判断用  

（厳密に「残日数≤30」＋別途LT在庫を足す形に変える場合は §13 で差し替え。）

### 9.2 通知

| 項目 | ロック |

| 手段 | メール |
| 宛先 | 運用メール（Script Property 等に保持。例: 社長Gmail）。docs に平文固定しない運用を推奨 |

### 9.3 発注書下書き（第1版に含む）

- アラート対象の単品JANについて発注書下書きを生成する。
- 推奨発注量の仮式: `max(0, ceil(発注点在庫 × 係数 − 実在庫))`。係数やまとめ発注単位は仕入先都合で調整（未ロックは §13）。
- **送信・発注確定は人**。システムは下書きまで。

### 9.4 Runbook との関係

- 日次: メールで届く（自動）。
- 週次月曜「在庫アラート確認」: メール漏れ・下書き未処理の棚卸しに残す。
- 週次火曜「発注判断」: 下書きを見て発注実行。

## 11. 非機能・聖域

### 11.1 非機能

- 日次バッチ。タイムゾーン Asia/Tokyo。
- 監査ログ: 実行日時・対象件数・差分サマリ・モール別成功/失敗。
- シークレット・トークンは Script Property／ローカル秘匿のみ。要件・ログに生値を書かない。
- 冪等・再実行安全（同じ日に再実行してよい）。

### 11.2 第1版で絶対に触らない聖域

- 楽天CSV生成ロジックおよび聖域コメント付きコード
- Amazon 出品 PUT／承認①②／Lv4 オーケストレーション本体
- Yahoo 出品・説明APIの本線
- inventory-app の棚卸・スキャン・入出荷 UI
- リサーチ① GAS・競合価格本線
