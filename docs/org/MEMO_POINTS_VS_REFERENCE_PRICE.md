# メモ: ポイント付与と「過去価格／参考価格」・売価引き上げの考え方

**日付**: 2026-08-12

**関連**: [D_MENU_AMAZON_DEALS_BULK_REQUIREMENTS.md](D_MENU_AMAZON_DEALS_BULK_REQUIREMENTS.md) §10.10／（改訂予定）売価一発＋ポイント減衰の実質価格戻し  
**扱い**: **運用・設計の参考**。数値・期間は Amazon 側が予告なく変わる。本番判断前に SC ヘルプ／申請画面の現行表示を再確認すること。

## 1. 記事の主張（要約）

外部メルマガ／ノウハウ記事の骨子（一次ソースは Amazon ヘルプ引用を自称）。

| 主張 | 内容 |
|------|------|
| 過去価格の足かせ | セール・クーポン・直接値下げは「最近この値段だった」基準に残り、次の大型セールで値上げしにくい／取消線やプライム限定が通らない |
| 過去価格を汚す施策 | ①販売価格の直接変更 ②クーポン ③タイムセール／プライム限定割引（記事は「過去30日最低価格を基準」と記載） |
| ポイントだけ例外 | 出品者の「ポイント付与率／ポイント数」は **参考価格・過去価格の算出に影響しない**（公式ヘルプ引用と主張） |
| 運用示唆 | 価格は据え置き、ポイントで実質安く見せる。3%では弱い→**20%以上**が「買う理由」になりやすい（原資は出品者負担） |
| 時期 | セールの数週間前など「価格をいじりたくない」期間に、ポイントだけ上げて売上を落とさず申請しやすい状態を保つ |

設定UI（記事）: 在庫→Points／ポイントセントラル→出品一覧→ポイント%（現行UIはポイントセントラル本線。在庫画面から直接は旧仕様の可能性あり）。

## 2. 事実確認（公式文言）

### 2.1 調査対象の引用

記事が「公式ヘルプ」として示す文言:

> 出品者が設定する「ポイント付与率」や「ポイント数」は、参考価格・過去価格の算出には影響しない

### 2.2 調査結果（2026-08-12）

| 項目 | 結果 |
|------|------|
| 上記**一字一句**のヘルプページ | **未特定**。Seller Central ヘルプは多くがログイン壁で、公開クロールでは当該ページ ID／URL を確定できず |
| 二次情報の一致 | **強い**。代理店・運用ブログが同趣旨を繰り返し記載（例: ポイントは販売価格を動かさないため WAS／参考価格を毀損しにくい／影響しない） |
| 論理的整合 | **高い**。参考価格・Was／Typical は「販売価格・取引価格・プロモ価格」系の履歴が主。ポイント%は別チャネル（ポイントセントラル／Pointsフィード）で、**販売価格フィールドを変更しない** |
| 注意 | 「内部のカート評価で実質値下げ同等に見る」等の**別ロジック**と混同しない。本メモの対象は **参考価格／過去価格（取消線・Deal上限の土台）** |

**判定（社内メモ用）**:

- **運用仮説として採用可**: 「ポイント付与は過去価格を汚しにくい／汚さない」は、記事・業界二次情報・仕組み上の整合から **妥当性が高い**。
- **公式一次ソース確認ステータス**: **未完了**（ログイン後にヘルプ検索で原文ヒットを取る作業が残る）。ヒットしたら本メモに **ヘルプタイトル／URL／取得日** を追記する。
- 実装・社長説明では「公式で確認済みの確定事実」ではなく、**「二次情報＋論理で支持。SCで原文確認待ち」** と書く。

### 2.3 ログイン後の確認手順（人間）

1. SC → ヘルプで `ポイント` `参考価格` `過去価格` を検索  
2. 上記引用に近いページを開き、スクショ／URLを本メモへ  
3. 参考: ポイントセントラル／ポイントフィード関連ヘルプ、参考価格（Was／Typical／List）関連ヘルプを併読

## 3. 「8週間ルール」と売価引き上げ（参考要約）

ユーザー理解: 「タイムセールの価格を引き上げたかったら **8週間は我慢**しないと引き上げられない」。

### 3.1 調査で分かったこと

| ルール候補 | 内容 | 公式度 | 本PJへの意味 |
|------------|------|--------|--------------|
| **Deal の過去30日最低** | おすすめ／数量限定等の Deal 上限は、**直近約30日の最低価格**等を土台に割引条件を課す、という説明が二次情報で多い | SC申請画面・ヘルプ依存（ログイン要）。記事も「過去30日」と記載 | 「安く刻むと次の Deal 上限が下がる」。**30日は公式寄りでよく出る数字** |
| **参考価格 90日中央値** | Was／Typical は多くの説明で **直近90日の（非プロモ）中央値** | グローバル参考価格ポリシー説明と一致しやすい | 「すぐ値上げしても、履歴が残ると取消線・申請の土台が低いまま」 |
| **90日中45日超の低価** | 2026-05頃の更新として、90日のうち半分超が低価だとプロモ価格も中央値計算に混ぜる、等 | 英語圏・跨境二次情報で広く報道。JP文言は要SC確認 | 「安売り日数が多いと参考価格が沈む」 |
| **「8週間」そのもの** | **公式ヘルプ上の固定ルールとしては未発見** | 未確認 | **慣用・バッファ**の可能性大（例: 30日窓＋余裕、または約2か月据え置き） |

### 3.2 考え方のメモ（設計参考）

```text
タイムセール（Deal）で販売価格を下げると
  → 「過去○日の最低／参考価格」土台が下がる
  → 次に「高く申請したい」ときに上限が上がらない／取消線が弱い

だから:
  - 価格そのものを頻繁に下げない
  - 実質の安さはポイントで出す（§2 の仮説）
  - どうしても売価を上げて次の Deal に備えたいなら、
    「窓（30日や90日）が塗り替わるまで据え置きが必要」
    ※「8週間」は公式固定ではなく、その我慢期間の目安として扱う
```

**社長向け一文**:  
「Deal で安くすると次のセールで上げにくい」は実務的に正しい。数字の正本は SC の申請上限表示とヘルプ。**8週間は公式ラベルではなく、我慢期間の目安**としてメモする。厳密には **30日窓（Deal）と90日窓（参考価格）** を分けて考える。

## 4. 本PJ方針との接続（途中メモ）

Ask で固めた方向（売価は目標へ一発、その後ポイント減衰で実質価格を戻す）と、本記事は **同方向**:

| 方針 | 記事／調査との関係 |
|------|-------------------|
| 売価を安く刻まない | 過去価格・Deal上限を守る |
| ポイントで実質割引 | 過去価格を汚しにくい手段（仮説・二次支持） |
| B（Deal）は赤札用途 | Deal 自体は過去価格／30日最低に効く → **回数・深さは計画的に** |
| B後に売価スナップ＋高ポイント→減衰 | スナップは「正規売価に戻す」。減衰はポイント側。Deal 直後の売価連続安売りを避ける |

**矛盾しうる点（要設計）**:

- B（タイムセール）自体は記事の言う「汚す施策」。ポイント戦略は **Deal の代替／前後の補助**であり、Deal をゼロにはしない本PJでは「Dealは限定的・ポイントで稼ぐ」のバランスが必要。
- 旧実装の「our_price 段階上げ」は、上げる過程で履歴に中間価格が残る可能性 → 本記事の問題意識とも噛み合わず、**廃案方向が妥当**。
